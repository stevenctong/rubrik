The workflow

Four programs, one CSV contract between each pair.

An operator builds an inventory once, filters it down to a recovery wave, triggers the wave, then watches it finish. Live mounts get unwound afterwards. Each step hands the next a CSV, which is what makes the whole thing restartable.

StepProgramProduces
1. Inventory get_ahv_inventory.py ahv_inventory_<ts>.csv plus ahv_containers_<ts>.csv
2. Filter You, in a spreadsheet A wave CSV, with the two blank trailing columns filled in
3. Trigger ahv_mass_recovery.py
or the Ansible role		 <wave>_state_<ts>.csv, named after the wave
4. Monitor ahv_monitor_recovery.py ahv_recovery_results_<ts>.csv plus a metrics summary
5. Unwind ahv_cleanup_mounts.py Live mounts torn down
Why the inventory CSV ends with two blank columns

target_container_name and recovered_vm_prefix are written empty on purpose. Filling them in is the whole of step 2, which makes the inventory double as the wave template rather than a separate format to learn.

The pipeline

Four calls to trigger, regardless of wave size.

The CDM recovery API is natively batched. Two VMs and five hundred VMs cost the same number of round trips — only the request bodies get longer. That is why nothing here loops per VM to start a recovery.

Where state lives

The central design idea, and the reason Ansible does not monitor.

A fifty-VM wave can take hours. Something will interrupt it: a laptop sleeping, an SSH session dropping, a terminal being closed. The question is whether that interruption loses the job identifiers, because without them there is no way to find the recoveries again.

Why Ansible cannot hold this state

  • until / retries is an in-memory loop. No checkpoint, no resume.
  • .retry files record failed host names only — not job identifiers.
  • async / async_status targets long-running commands on remote hosts. Our uri call returns in milliseconds, so wrapping it buys nothing.
  • Task output is buffered. A retries: 480 poll prints nothing for hours.
  • Closing the terminal sends SIGHUP and kills the run.

Python or Ansible

Both trigger. Only Python monitors.

Python

The complete path

  • Inventory, trigger, monitor, cleanup
  • Resumable monitoring with metrics
  • Auto-discovers staged CSVs
  • Stdlib only, Python 3.6 compatible

Ansible

Trigger only, then hands off

  • Waves defined as inventory groups
  • Reusable rubrik_cdm_auth role
  • --check is a genuine dry run
  • Settings in a gitignored extra-vars file

Reach for Ansible when the team already lives there and wants waves expressed as inventory files. It resolves, triggers, writes the wave-state CSV, and exits in minutes rather than hours. Monitoring then belongs to ahv_monitor_recovery.py, which can be started, stopped, and restarted freely.

The per-VM lookup loop is serial

Ansible parallelises across hosts via forks, never across loop items, and this play runs on a single host. Tens of VMs is fine; hundreds is slow. Setting ahv_inventory_csv drops it to zero API calls, which is the intended path at scale.

Staged lookups

What can be resolved from a file, and what cannot.

LookupStageableHow
VM name to id Yes --inventory / ahv_inventory_csv
Storage containers Yes --containers / ahv_containers_csv, worth it for the 5.3s cold call
AHV cluster list Skipped 120 to 403ms does not justify the config surface
Closest snapshot No Point in time varies per run. Inherently runtime.
Event series id No Job ids do not exist until trigger — but cached back after first resolution

Auto-discovery, and why only in Python

Because inventory filenames carry timestamps, always passing a full path means pasting a new one every run. The Python trigger picks the newest matching file beside itself and always says which one it chose: 

Using inventory CSV: ahv_inventory_20260910_120000.csv (22.8 hours old)
Using containers CSV: ahv_containers_20260910_120000.csv (22.8 hours old)

Past a week it warns rather than quietly using stale data:

Using inventory CSV: ahv_inventory_20260101_000000.csv (253.4 days old)
WARNING: that inventory CSV is 253.4 days old. Re-run get_ahv_inventory.py if the
         environment has changed, or pass an explicit path.

Age is read from the YYYYMMDD_HHMMSS stamp in the filename rather than mtime, because copying an old inventory between machines resets mtime and would make a stale file look freshly generated — defeating the warning. Ansible deliberately stays explicit: a scheduled run silently picking up a different file is a worse failure than typing a variable once.

Design decisions

The choices worth explaining to whoever inherits this.

Status is matched by prefix, not enumerated

The captured session contains no failed or cancelled recovery, so the terminal failure strings are unconfirmed. Rather than hardcode an enum that might be wrong, anything starting Success, Fail, or Cancel classifies accordingly and everything else counts as in flight. Unrecognised values are logged verbatim instead of being silently bucketed.

Missing snapshots are excluded loudly

A VM with no snapshot at the requested point in time is written to an exclusions CSV with a reason, never dropped. During a recovery event, a wave that quietly covers fewer VMs than you asked for is the worst possible outcome.

Stdlib only

No requests, no third-party packages, %-formatting throughout for Python 3.6 compatibility. These scripts run on whatever jump host is available during an incident, which is not the moment to discover a missing pip dependency.

The wave-state CSV is patched, not rewritten

When the monitor caches a resolved event_series_id, it edits that cell in place rather than regenerating the file from memory. The monitor does not track every column — container_natural_id, recovered_vm_prefix, container_natural_id — and rewriting would silently drop them.

Commands

The order to exercise things in.

Python

# 1. Build the inventory -- proves auth, pagination, and both CSVs
python3 get_ahv_inventory.py --svc_json rsc-sa.json --cluster 10.8.48.104 --detail

# 2. Dry run -- resolves everything, prints the request body, POSTs nothing
python3 ahv_mass_recovery.py --svc_json rsc-sa.json --cluster 10.8.48.104 \
    --csv wave1.csv --method mount --container default-container \
    --recovered_vm_prefix dr --dry_run

# 3. Live mount two VMs and watch them finish
python3 ahv_mass_recovery.py --svc_json rsc-sa.json --cluster 10.8.48.104 \
    --csv wave1.csv --method mount --container default-container \
    --recovered_vm_prefix dr --monitor

# 4. Monitor separately -- resumable, survives Ctrl-C and terminal close
python3 ahv_monitor_recovery.py --svc_json rsc-sa.json --cluster 10.8.48.104 \
    --state wave1_state_20260916_062714.csv

# 5. Verify mounts BEFORE trusting the delete path
python3 ahv_cleanup_mounts.py --svc_json rsc-sa.json --cluster 10.8.48.104 --list_only

Ansible

# Settings once, in a gitignored file
cp vars/example-recovery-vars.yml vars/my-recovery.yml

# Dry run
ansible-playbook -i inventory/wave1.yml ahv_mass_recovery.yml \
    -e @vars/my-recovery.yml --check

# Trigger, then hand off to the Python monitor
ansible-playbook -i inventory/wave1.yml ahv_mass_recovery.yml \
    -e @vars/my-recovery.yml

# Same settings, export instead -- a later -e wins
ansible-playbook -i inventory/wave1.yml ahv_mass_recovery.yml \
    -e @vars/my-recovery.yml -e ahv_method=export
Rehearse with live mount

Live mount is non-destructive and easy to unwind, which makes it the right method for a first run against any cluster. That is how the write path here was proven. Note that live mount reports no dataTransferred; export does, once the job reaches a terminal state.
