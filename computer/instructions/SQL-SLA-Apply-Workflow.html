SQL Server — SLA Apply Workflow

Inventory, then apply: production workflow and API reference for Set-SLA-SQL-Fileset.ps1 (SQL instances)

1. Overall Workflow

SLAs are assigned to SQL instances, not hosts. RSC attaches protection to each MssqlInstance object under a SQL host, so the script resolves every host on your list to its instances and assigns one SLA to all of them. The work splits into two runs: an optional inventory run that snapshots the environment to a CSV, and an Apply run that assigns the SLA, either from that CSV or by querying RSC live. A SQL run works on one cluster, given by the required -clusterName: every host lookup, the inventory and every assignment call are limited to it.

Prerequisite: every host on your list must already be added to Rubrik, and SQL discovery must have finished so its instances appear in RSC. The script does not add hosts. In a live run, a host that is not found, or that has no SQL instances, stops the run before anything is changed. Every run also needs -clusterName, the exact name of the one cluster to work on. Without it the script stops with "Runs need -clusterName. Every lookup, and every assignment call, is on that one cluster." (and, for the inventory, "-getSqlInventory needs -clusterName. The SQL inventory covers one cluster.").

Why an inventory CSV: in a large estate, finding every host, instance and ID with GraphQL on each production run is slow and repeats work. With the inventory CSV the Apply run skips the host search and instance lookup and uses the saved host and instance IDs. It also trusts the SLA state saved in the CSV and does not read each instance's state again: you pass the inventory as the starting state. An instance whose saved SLA already matches the target is skipped. Refresh the inventory if SLAs may have changed since it was taken.

2. Script Logic (Pseudocode)

INVENTORY RUN  (-getSqlInventory, optional host list; needs no -action, SLA or confirmation)
    VALIDATE: -clusterName must be given (the script stops without it), and the apply and SLA parameters are rejected
    AUTHENTICATE to RSC
    LOOK UP the cluster named by -clusterName; STOP if none, or more than one, matches
    LIST SQL hosts on that cluster only (all of them, or only the hosts named), each with its cluster and non-archived instances, and each instance's
         effective SLA and any pending SLA
    WRITE one CSV row per instance (a host with no instances gets one "Host" row)
    EXIT

APPLY RUN  (-action Apply)
INPUT: hosts (-sqlHosts, or -sqlCsvPath which wins if both are given; -inventoryCsv supplies the IDs and state),
       one SLA (-slaName or -slaID) that applies to every host,
       required -clusterName (the one cluster everything is looked up and assigned on),
       optional -applyMode Bulk|Single, -batchSize, -skipPolling, -assignLog, -dryRun, -skipConfirm,
       -assignMutation AssignSla|AssignSlasForSnappableHierarchies, -pollIntervalSec, -timeoutSec,
       -inventoryMaxAgeHours, -csvOutputPrefix
       (parameters are validated first, see section 5; a run with no parameters prints a usage summary and EXITs 0)

STEP 0   AUTHENTICATE to RSC using the Service Account JSON (client_id/client_secret -> bearer token)
STEP 1   LOOK UP the cluster named by -clusterName (required); STOP if none, or more than one, matches
STEP 2   RESOLVE the SLA name to its ID (DO_NOT_PROTECT and NO_ASSIGNMENT need no lookup; -slaID is used as given)

STEP 3   GET INVENTORY (SQL hosts on the -clusterName cluster and their instances, each with its effective SLA and any pending SLA)
IF -inventoryCsv was given, from the CSV:
    READ the CSV; check it is a SQL inventory; print its age, warn if older than -inventoryMaxAgeHours
    KEEP only the hosts the inventory has on the -clusterName cluster (warn about the others)
    IF a host list was given:
        a listed host that is not in the inventory for that cluster is skipped ("not in inventory"; the console says
            when it is in the inventory on a different cluster)
        a listed host that is in the inventory but has no instances is an error
    ELSE: use every host in the inventory for that cluster (a host with no instances is skipped with a warning)
    a host name that appears under more than one host ID in the CSV is an error
    take each instance's assignment, effective SLA and pending SLA from the CSV columns
    IF any error: print it and STOP before changing anything
ELSE, from RSC, FOR EACH host name:
    LOOK UP the SQL host by name on the -clusterName cluster; require exactly one exact-name match
    COLLECT its cluster and its non-archived SQL instances (id, name, assignment, effective SLA, pending SLA)
    IF the host is not found or has no instances: record an error
    IF any host had an error: print them and STOP before changing anything

STEP 4   DECIDE what is skipped, from the state gathered in Step 3 (live from RSC, or the CSV columns with -inventoryCsv).
    Three things are skipped, and the plan, the console and the Apply CSV say which and why:
    a host that is not found / not in the inventory for the cluster   (a live run stops instead, before any change)
    an instance with ANY pending SLA                      -> SkippedPending (an assignment is already in flight)
    an instance whose effective SLA is already the target -> AlreadyOnTarget (assigned directly or inherited)
    everything else is ASSIGNED   (the pending check comes first)
    IF no instance was found at all and no host was skipped for not being in the inventory: STOP with an error

STEP 5   PRINT the plan: hosts, instances, how many to assign, what is skipped and why, number of calls
    IF -dryRun: STOP, no changes
    ASK the user to type YES, otherwise STOP        (exactly YES, upper case; only asked when something is to be assigned;
                                                     -skipConfirm skips the question and goes ahead; the plan is still printed)
    CREATE the Apply CSV (every instance's starting SLA, status Pending) before changing anything

STEP 6   BUILD call groups from the instances to assign (all on the one -clusterName cluster):
    Bulk (default): batches of up to -batchSize (default 50) instance IDs
    Single:         one group per host
    (an instance ID is sent only once per run; an instance with no cluster ID stops the run with an error before any call)
STEP 7   FOR EACH group: SEND the assignment mutation with that group's instance IDs
    ON failure: mark the group CallFailed and continue with the next group
    ON success: mark the instances Submitted

STEP 8   IF not -skipPolling:
    LOOP every -pollIntervalSec until all Submitted instances show the SLA or -timeoutSec is reached:
        READ the state of the instances still waiting (one batched query)
        PRINT "n/total effective, s elapsed"
    MARK each instance Applied or Timeout

STEP 9   REWRITE the Apply CSV with each instance's outcome and its host's status
    IF the hosts came from -sqlCsvPath: WRITE each host's outcome into the CSV's "executed" column (keep a .bak of the original)
    PRINT a note for instances skipped for a pending SLA, and a warning for hosts skipped for not being in the inventory
    EXIT 1 if any instance is CallFailed, Timeout or NotAttempted, or the run stopped with an error, otherwise EXIT 0
         (a skip, for a pending SLA or a host not in the inventory, does not by itself change the exit code,
          unless every listed host was skipped, which exits 1)

3. Detailed Steps & GraphQL Reference

Each step corresponds to a function or logic block in Set-SLA-SQL-Fileset.ps1. Every GraphQL call is a POST to <base URL>/api/graphql with the body { "query": ..., "variables": ... }. The Variables blocks show the full variables object the script sends.

REST

0Authenticate to RSC

The script reads the RSC Service Account JSON (-RscServiceAccountJson), confirms it contains client_id, client_secret and access_token_uri, and exchanges them for a bearer token. It requires PowerShell 7+. This is the same block as computer/Core/RSC-Authentication.ps1, copied inline.

MethodPOST
URL<access_token_uri from the service account JSON>

Request body

{
  "grant_type": "client_credentials",
  "client_id": "<from service account JSON>",
  "client_secret": "<from service account JSON>"
}

The tenant base URL is access_token_uri with /api/client_token removed. Every later call is a GraphQL POST to <base URL>/api/graphql with an Authorization: Bearer <access_token> header. The service account needs permission to view SQL hosts and instances, view SLA Domains, and assign SLAs.

Query

1Resolve -clusterName to a cluster ID (required)

Function: Get-ClusterIdByName

SQL runs work on one cluster. -clusterName is required and limits the host lookup (Step 3) and every assignment call to that cluster. The name is looked up once at the start (before the SLA name is resolved in Step 2) and turned into an ID, because the host lookups filter by CLUSTER_ID. The run stops before any change if no cluster, or more than one cluster, has that exact name. It is required for every SQL run (Apply, Test and -getSqlInventory). Without it the script stops with "Runs need -clusterName. Every lookup, and every assignment call, is on that one cluster." The inventory run does the same lookup itself, first, after it authenticates (see step I1 in section 4).

query ClusterByNameQuery($filter: ClusterFilterInput) {
  allClusterConnection(filter: $filter, sortBy: ClusterName, sortOrder: ASC) {
    nodes {
      id
      name
    }
  }
}

Variables

{
  "filter": { "name": ["vault-r-madison"] }
}

The name filter can match partially, so the script keeps only the cluster whose name matches exactly. A host that is on a different cluster is not found by the Step 3 lookup, so it is reported as an error before anything changes, and the same host name on two clusters no longer clashes. Run once per cluster.

Query

3Get Inventory: each SQL host, its instances, and each instance's SLA state

Function: Get-SqlHostInstances (skipped when -inventoryCsv is used)

One call per host name, paginated 100 at a time. The NAME filter can match partially, so the script keeps only the host whose name matches exactly (case-insensitive) and stops with an error if there are none or several. The instances come back under the host, with their current assignment, effective SLA and any pending SLA, so no second lookup is needed. Archived instances are excluded. The host's own SLA is not used, because SQL protection is on the instances. Because -clusterName is required, a CLUSTER_ID filter (the cluster ID from Step 1) is always sent, so a host on another cluster is reported as not found. The host's cluster comes back too and is shown in the plan and the CSVs. Every host is on the -clusterName cluster.

query MssqlHostInstancesQuery($first: Int!, $after: String, $filter: [Filter!], $instanceFilter: [Filter!]) {
  mssqlTopLevelDescendants(after: $after, first: $first, filter: $filter, sortBy: NAME, sortOrder: ASC, typeFilter: [MSSQL_HOST]) {
    edges {
      cursor
      node {
        id
        name
        objectType
        ... on MssqlHost {
          cluster { id name }
          instanceDescendantConnection: descendantConnection(filter: $instanceFilter, typeFilter: [MssqlInstance]) {
            edges {
              node {
                id
                name
                slaAssignment
                effectiveSlaDomain { id name }
                pendingSla { id name }
              }
            }
          }
        }
      }
    }
    pageInfo { endCursor hasNextPage }
  }
}

Local logic

4Decide what is skipped

No API call. Every instance already carries its SLA state from the lookup in the previous step: its assignment type, its effective SLA, and any pending SLA (live from RSC, or from the inventory CSV). The script uses that to decide, for each instance, whether to assign the target SLA or leave it. Three things are skipped, and the plan, the console and the Apply CSV say which and why:

SkippedWhenWhere it shows
Host not foundWith an inventory, a listed host that is not in the inventory CSV for the -clusterName cluster (including a host the inventory has only on another cluster). (In a live run a host that is not found stops the run instead, before any change.)Plan, end-of-run warning, a NotInInventory row in the Apply CSV
Pending SLAThe instance has any pending SLA. An assignment is already in flight, and sending another would only queue a second pending action.Plan action Skip: pending, status SkippedPending, a note at the end of the run
Already on the targetThe instance's effective SLA is already the target, whether it was assigned directly or inherited. Plan action Skip: on target, status AlreadyOnTarget

How "already on the target" is checked, by target:

TargetAlready on target when
An SLA DomaineffectiveSlaDomain.id equals the SLA ID
DO_NOT_PROTECTeffectiveSlaDomain.id == "DO_NOT_PROTECT"
NO_ASSIGNMENTslaAssignment is not "Direct", so the instance already inherits
  • The pending SLA is checked first, so an instance with a different SLA pending is skipped too. Rerun once it has finished.
  • An instance that is on the target by inheritance is skipped, so no direct assignment is added on top of it.
  • With -inventoryCsv the state comes from the saved columns slaAssignment, effectiveSlaId and pendingSlaId, with no RSC call. An inventory written before the pending columns existed has none, so every instance reads as having nothing pending. Create a new inventory to get the pending check from a file.
  • The completion polling in Step 8 asks a different question: whether the assignment has finished, where a pending SLA does mean "not yet". It uses its own query, shown there.
Local logic

5Plan, confirm, and create the Apply CSV

No API call. The script prints the plan: a few summary lines (source, workload, mutation, target SLA, apply mode, whether polling is on, how many hosts and instances, how many calls, and everything that will be skipped and why), then a table with one row per instance. The columns are hostName, cluster, object, action, currentSla, pendingSla and assignment. The action is one of:

actionMeaning
AssignThe target SLA will be sent
Skip: on targetThe effective SLA is already the target
Skip: pendingAn SLA is already pending on it, so nothing is sent

The cluster column shows the cluster each instance is on (the -clusterName cluster). The plan's call count uses the same grouping as the real run, so it shows the number of calls that will actually be sent.

  • -dryRun stops here, nothing changes.
  • The script asks you to type YES (exactly, upper case) before it changes anything. Anything else cancels, exits 0 and writes nothing. If there is nothing to assign (every instance is already on the target or skipped), there is nothing to confirm and no calls are made.
  • To skip the prompt and just run it, add -skipConfirm. The plan is still printed and the Apply CSV is still written before any change. Only the question is skipped, so use it for a run you have already previewed with -dryRun, or for an unattended run. It applies to -action Apply.
  • Before any change, the Apply CSV is created with every instance's starting assignment and SLA (status Pending). This is the rollback record, and it is rewritten with the results at the end. The script never reverts anything itself.
Local logic

6Build the call groups

No API call. The instances that still need the SLA are split into groups, and one assignment call is sent per group.

-applyModeGroupsExample: 120 instances on 6 hosts, all on the -clusterName cluster, batch size 50
Bulk (default)The instances are split into batches of up to -batchSize instance IDs (default 50).3 calls: 50, 50 and 20 instances
SingleOne group per host, holding all of that host's instances6 calls, one per host

Where the instance IDs come from. The IDs sent in each call are the IDs of the SQL instances (not the host IDs). They come from the Get Inventory step (Step 3): the live host lookup, or the inventory CSV. Instances already exist and nothing is created in a SQL run, so there is no second lookup.

An instance ID is sent only once per run, because the same ID twice in one call can fail validation for the whole batch. If an instance to assign has no cluster ID, the run stops with an error before any call, because it could not be batched safely.

Calls are sent one after the other. A failed call marks only that group CallFailed; the remaining groups still run.

Mutation

7Apply the SLA for all instances

Function: Set-ObjectSla

Two mutations are supported and a run uses only one of them, so no object is sent to both in the same run. The default is assignSla. -assignMutation AssignSlasForSnappableHierarchies selects the one the RSC UI uses. Both take the same object IDs. The object IDs are instance IDs, not host IDs. The call returns as soon as RSC accepts it; RSC applies the change afterwards (Step 8).

Check the first SQL run: assignSla has been confirmed on Windows filesets on one cluster but not yet on SQL instances, so add -assignLog the first time you use it on SQL, or choose -assignMutation AssignSlasForSnappableHierarchies.

Default: assignSla

Query

8Poll until RSC shows the SLA

Function: Wait-SlaEffectiveWithProgress (skipped with -skipPolling, alias -noWait)

The assignment mutation is asynchronous. success: true only means RSC accepted the request. In a captured UI session the effective SLA kept its old value, with the new SLA shown as pendingSla, for tens of seconds to minutes before both flipped together. The script therefore polls the instances it submitted, with the batched query shown below, every -pollIntervalSec seconds (default 5), until each one is effective or -timeoutSec (default 600) runs out in total.

An instance counts as effective only when nothing is pending on it and:

TargetEffective when
An SLA DomainslaAssignment is Direct and effectiveSlaDomain.id equals the SLA ID
DO_NOT_PROTECTslaAssignment is Direct and effectiveSlaDomain.id is DO_NOT_PROTECT
NO_ASSIGNMENTslaAssignment is not Direct

With -skipPolling none of this runs: no polling query is sent and every accepted instance ends as Submitted.

Variables (one entry for each instance still waiting)

{
  "id0": "fbe7c3e4-44e1-5475-af41-f10d863f7c87"
}
  • Each poll sends one batched query for only the instances still waiting (shown below).
  • It prints a progress line each time, for example 12/40 effective, 95s elapsed.
  • A failed poll is reported and retried at the next interval; it does not stop the run.
  • Timing is only as precise as the poll interval.

Each poll asks for many objects at once using GraphQL aliases (o0, o1, ...), at most 50 per request, so the query text and the variable names grow with the number of objects. It returns each object's assignment type, effective SLA and any pending SLA. The instances both support these fields.

query PendingSlaBatchQuery($id0: UUID!, $id1: UUID!) {
  o0: hierarchyObject(fid: $id0) {
    id
    slaAssignment
    effectiveSlaDomain { id name }
    ... on CdmHierarchyObject { pendingSla { id name } }
  }
  o1: hierarchyObject(fid: $id1) {
    id
    slaAssignment
    effectiveSlaDomain { id name }
    ... on CdmHierarchyObject { pendingSla { id name } }
  }
}

Output

9The Apply CSV, host status, and exit code

Each Apply run writes one CSV, <prefix>sql_sla_apply-<timestamp>.csv. The timestamp includes seconds, so two runs never share a file. The file is written twice:

  • Before any change, right after you confirm, with one row per instance: its starting assignment and SLA, and status Pending. If the run is interrupted, this file still holds the starting state, so it is the rollback record. The script never reverts anything itself.
  • At the end, rewritten with each instance's outcome and the status of its host. A host with no instance to show, such as one that is not in the inventory, gets a row with no object.

The file is written to a temporary file and moved into place, so a failure part way cannot leave a half-written CSV. A -dryRun, or answering anything other than YES, writes no file.

One special case: if the host list came with -inventoryCsv and none of the listed hosts is in the inventory, the script writes a short Apply CSV with only the columns workload, host, object, objectId, hostStatus, status, error, one NotInInventory row per host, and exits 1.

Columns: workload, host, cluster, hostStatus, object, objectId, beforeAssignment, beforeSla, beforeSlaId, beforePendingSla, targetSla, assignMutation, applyMode, callGroup, callSec, effectiveSec, status, error. The cluster is the host's cluster, the before* columns are the starting state (beforePendingSla is any SLA that was pending), callGroup and callSec say which call carried the instance and how long it took, and effectiveSec is how long after the first call RSC showed the SLA.

The console prints the same results as counts by status and by host status, lists any instance that needs attention, lists the instances skipped for a pending SLA, and warns about hosts that were skipped for not being in the inventory. If the hosts came from the host CSV, its executed column is updated too (see section 4). A Timeout does not mean the assignment failed, only that it was not visible in time, so check those instances in RSC.

Exit code. 1 if any instance is CallFailed, Timeout or NotAttempted, if the run stopped with an error after the Apply CSV was created, or if every listed host was missing from the inventory. Otherwise 0, including a -dryRun, a cancelled prompt, a run where nothing needed assigning, and runs with hosts or instances skipped. A problem found before any change (host not found, no instances, bad parameters, unreadable inventory) stops the script with an error and no assignment is made. Nothing is ever reverted.

Local logic

HThe host CSV and the executed column

Hosts can be given on the command line (-sqlHosts) or in a CSV (-sqlCsvPath). The CSV holds only the host names and the run's state. The SLA is not in the CSV: it is given with -slaName or -slaID and applies to every host in the file. If both -sqlHosts and -sqlCsvPath are given, the CSV wins and -sqlHosts is ignored, with a note printed.

After an Apply run the script writes each host's outcome into the executed column of the same file, as a status followed by the time. The column is added if it is missing.

  • The file is written to a temporary file and then moved into place, and the original is kept once as <file>.bak. If the write fails, the script says so and the results are still in the Apply CSV.
  • The write uses standard CSV quoting, so every field ends up in quotes even if the original had none. Excel and PowerShell read it the same.
  • A rerun does not skip hosts that already have a value in executed. It processes every host again and overwrites the column. Skipping completed hosts is not built.
Query

I1Create the inventory: -getSqlInventory

Function: Get-AllSqlHostInstances

A read-only switch. It needs no -action, no SLA and no confirmation, and it rejects the action, SLA and apply or test parameters if you pass them. It lists every SQL host on one cluster and each host's instances with the current SLA, writes a timestamped CSV, and exits. With no host list it covers every host RSC returns for that cluster; with -sqlHosts or -sqlCsvPath it is limited to those hosts, and a named host that is not found only prints a warning. It can be limited with the SQL host parameters only, not the fileset ones.

./Set-SLA-SQL-Fileset.ps1 -RscServiceAccountJson ./rsc-sa.json -getSqlInventory -clusterName 'vault-r-madison'
./Set-SLA-SQL-Fileset.ps1 -RscServiceAccountJson ./rsc-sa.json -getSqlInventory -clusterName 'vault-r-madison' -sqlHosts sql01,sql02

-clusterName is required with this switch (without it the script stops with "-getSqlInventory needs -clusterName. The SQL inventory covers one cluster."). The name is looked up first (the Step 1 query) and turned into a cluster ID. The host query below then carries a CLUSTER_ID filter for that cluster, so the file covers that one cluster only. The run stops, and writes no file, if no cluster or more than one cluster has that name. The cluster columns stay in the CSV.

It uses the Step 3 query (host cluster and each instance's pendingSla included, only the edge cursor is left out). With no host list the NAME filter is left out and the pages are walked 100 at a time.

query MssqlInventoryQuery($first: Int!, $after: String, $filter: [Filter!], $instanceFilter: [Filter!]) {
  mssqlTopLevelDescendants(after: $after, first: $first, filter: $filter, sortBy: NAME, sortOrder: ASC, typeFilter: [MSSQL_HOST]) {
    edges {
      node {
        id
        name
        objectType
        ... on MssqlHost {
          cluster { id name }
          instanceDescendantConnection: descendantConnection(filter: $instanceFilter, typeFilter: [MssqlInstance]) {
            edges {
              node {
                id
                name
                slaAssignment
                effectiveSlaDomain { id name }
                pendingSla { id name }
              }
            }
          }
        }
      }
    }
    pageInfo { endCursor hasNextPage }
  }
}

I2Feed the inventory into Apply: -inventoryCsv

Function: Read-InventoryCsv

./Set-SLA-SQL-Fileset.ps1 -RscServiceAccountJson ./rsc-sa.json -action Apply `
  -inventoryCsv ./rubrik_sql_inventory-2026-11-11_090000.csv -sqlHosts sql01,sql02 -slaName 'Gold' -clusterName 'vault-r-madison'
  • The host and instance IDs come from the CSV. Step 3 is skipped: no host search, no instance lookup. Step 4 still runs, but on the saved state: the starting SLA state (assignment, effective SLA and any pending SLA) comes from the CSV, so an instance whose saved SLA already matches the target, or that has a saved pending SLA, is skipped without asking RSC. Step 1 (the cluster lookup) and Step 2 (the SLA name) still run, and the completion polling in Step 8 still reads RSC. If the inventory is stale, a skip or an assignment can be based on an old SLA, so refresh it when SLAs may have changed.
  • The file must be a SQL inventory with the expected columns, otherwise the run stops with a message saying which column or workload is wrong. If you give no host parameters, the workload is read from the file.
  • The script prints when the inventory was collected and warns if it is older than -inventoryMaxAgeHours (default 24).
  • Hosts on another cluster are not used. The saved clusterId of each host is compared with the -clusterName cluster. If the inventory has hosts on other clusters the script prints a warning ("The inventory has N host(s) on other clusters...") and leaves them out, and a listed host that is in the inventory only on another cluster is skipped like a host that is not in the inventory (a NotInInventory row, Skipped: not in inventory in the host CSV, and a console line that says it is on a different cluster). This keeps an inventory taken on the wrong cluster from putting an SLA on another cluster's hosts.
  • A listed host that is not in the inventory is skipped. The script prints a warning at the start and again at the end, and writes a NotInInventory row for it in the Apply CSV with the other hosts' outcomes. The rest of the list still runs. If every listed host is missing, nothing is assigned, the log is still written, and the script exits 1.
  • A listed host that is in the inventory but has no instances stops the run before any change. With no host list, a host with no instances is skipped with a warning instead, so one empty host does not block an environment-wide run.
  • With no host list, every host in the inventory on the -clusterName cluster is used.
  • Used with Apply only. -action Test needs live data, and -inventoryCsv is rejected there.

-clusterName is still required and the cluster is still looked up (Step 1). Use an inventory taken for the same cluster.

Instances added after the inventory was taken are not in the CSV and are not touched. Rerun the inventory after onboarding new hosts. An instance that was removed since the inventory is passed to the assignment call by its saved ID, and RSC decides what to do with it, so keep the inventory fresh.

Handling the inventory file: it lists host and instance names and IDs for your environment. Keep it out of any committed folder.

Input rules checked before anything is sent:

  • -RscServiceAccountJson is required. -action must be Apply or Test, unless -getSqlInventory is used.
  • Give hosts with -sqlHosts and/or -sqlCsvPath (the CSV wins). With -inventoryCsv and no host list, a SQL inventory is detected from the file. SQL and fileset parameters cannot be mixed, and the fileset-only options (including -recheckFilesetIDs) are rejected in a SQL run.
  • -clusterName is required for every SQL run (Apply, Test and -getSqlInventory). It is the exact name of one cluster, and the run stops if no cluster, or more than one cluster, has that name.
  • Give exactly one of -slaName or -slaID.
  • -batchSize, -pollIntervalSec and -inventoryMaxAgeHours must be 1 or greater.
  • -inventoryCsv only works with -action Apply and the file must exist.
  • -mode and -setHostLogRetention are rejected with Apply. -applyMode, -batchSize, -skipPolling and -assignLog are rejected with Test.
  • -getSqlInventory needs -clusterName and rejects -action, the SLA, the apply and test options, -inventoryCsv and the fileset options.

Every command also needs -RscServiceAccountJson <file>, and Apply commands need -action Apply. The script has a separate -action Test pathway that times Single versus Bulk assignment on test hosts. It is not part of the production flow and is not covered here.
