Fileset — SLA Apply Workflow

Inventory, then apply: production workflow and API reference for Set-SLA-SQL-Fileset.ps1 (filesets)

Two kinds of ID. The fileset template ID identifies the template itself, for example "Temp". It is what you give the script with -filesetTemplateId, and the same template has a different ID on each cluster. A fileset object ID identifies one fileset, which is the template applied to one host. The script finds those itself, and they are what it sends to the SLA assignment calls. You never pass a fileset object ID to the script.

1. Overall Workflow

A fileset is a fileset template (a name plus include, exclude and exception paths) applied to a host. SLAs are assigned to the fileset objects, so each host needs the fileset template applied to it before it can be protected. You give the script the template, by name (-filesetName) or by ID (-filesetTemplateId), and a list of hosts. For each host the script checks whether the template is already applied. Hosts that already have it are left alone. Hosts that do not get the template applied (with bulkCreateFilesets, after you confirm). Then the SLA is assigned to the filesets on all of those hosts. The script never creates or changes the template itself. A fileset run works on one cluster, given by the required -clusterName: the template lookup, the host lookup and the template application are all limited to it. The work splits into an optional inventory run that snapshots hosts, filesets and templates to a CSV, and an Apply run that applies the template where needed and assigns one SLA, either from that CSV or by querying RSC live.

Why an inventory CSV: finding every host, template and fileset (object) ID with GraphQL on each production run is slow and repeats work. With the inventory CSV the Apply run skips the template, host and fileset lookups and uses the saved IDs. It also trusts the SLA state saved in the CSV and does not read each fileset's state again: you pass the inventory as the starting state, and a fileset whose saved SLA already matches the target is skipped. Filesets created by applying a template in the same run are not in the CSV, so their IDs come from the template call itself (or from per-host lookups with -recheckFilesetIDs). Refresh the inventory if SLAs may have changed since it was taken.

2. Script Logic (Pseudocode)

INVENTORY RUN  (-getFilesetInventory, optional host list and -hostRoot; needs no -action, SLA or confirmation)
    VALIDATE: -clusterName must be given (the script stops without it), and the apply and SLA parameters are rejected
    AUTHENTICATE to RSC
    LIST every fileset template under -hostRoot
    LIST hosts (all of them, or only the hosts named), each with its cluster, and its filesets with their template, effective SLA
         and any pending SLA
    WRITE one row per template ("Template"), one per host ("Host"), and one per fileset ("Fileset")
    EXIT   (this path exits before the cluster is looked up, see step I1 in section 4)

APPLY RUN  (-action Apply)
INPUT: hosts from -filesetHosts, or from -filesetCsvPath (which wins if both are given)
       a fileset template, by -filesetName or -filesetTemplateId (the template, not a fileset on a host)
       optionally -inventoryCsv, which supplies the IDs and the starting SLA state
       one SLA (-slaName or -slaID) that applies to every host
       required -clusterName (the one cluster everything is looked up and applied on)
       optional -hostRoot, -applyMode Bulk|Single, -batchSize, -assignMutation, -assignLog, -skipPolling, -pollIntervalSec, -timeoutSec,
                -recheckFilesetIDs, -inventoryMaxAgeHours, -csvOutputPrefix, -dryRun, -skipConfirm

STEP 0   AUTHENTICATE to RSC using the Service Account JSON (client_id/client_secret -> bearer token)
STEP 1   LOOK UP the cluster named by -clusterName (required); STOP if none, or more than one, matches
STEP 2   RESOLVE the SLA name to its ID (DO_NOT_PROTECT and NO_ASSIGNMENT need no lookup)

IF -inventoryCsv was given: READ the CSV, check it is a fileset inventory, print its age, warn if older than -inventoryMaxAgeHours

STEP 3   GET THE TEMPLATE ID
    from the CSV:  FIND the template in the CSV's Template rows, by -filesetTemplateId or exact -filesetName
    from RSC:      LOOK UP -filesetName (exact, under -hostRoot, on the -clusterName cluster only),
                   or confirm -filesetTemplateId exists
    IF not found: STOP before any change, saying which host root and cluster were searched and whether a template with that name
    exists under the other host root

STEP 4   GET INVENTORY: the hosts, whether each has the template, and each fileset's SLA state
    from the CSV:  KEEP only the hosts the inventory has on the -clusterName cluster (warn about the others)
                   IF a host list was given, a listed host that is not in the inventory for that cluster is skipped ("not in inventory")
                   ELSE use every host in the inventory for that cluster
    from RSC:      FOR EACH host name: LOOK UP the host under -hostRoot on the -clusterName cluster; require exactly one exact-name match
    FOR EACH host:
        PICK the template that belongs to the host's cluster (must be exactly one)
        COLLECT the host's filesets for that template, each with its effective SLA and any pending SLA
        IF the host has none: it needs the template applied
    IF any host or template error: print them and STOP before changing anything

STEP 5   DECIDE what is skipped. Three things are skipped, and the plan, the console and the Apply CSV say which and why:
    a host that is not found / not in the inventory     (a live run stops instead, before any change)
    a fileset with ANY pending SLA                      -> SkippedPending (an assignment is already in flight)
    a fileset whose effective SLA is already the target -> AlreadyOnTarget (assigned directly or inherited)
    everything else is ASSIGNED

STEP 6   PRINT the plan: hosts that have the template, hosts that need it applied, filesets, how many to assign, what is skipped and
         why, number of calls (for the existing filesets)
    IF -dryRun: STOP, no changes, no files
    IF there is anything to assign or apply: ASK the user to type YES, otherwise STOP    (-skipConfirm skips the question and goes ahead; the plan is still printed)

STEP 7   IF any host needs the template:
    SEND one bulkCreateFilesets call with {hostId, templateId} for those hosts (all on the -clusterName cluster)
        ON failure: record TemplateFailed for those hosts (no object) and continue
    DEFAULT: CAPTURE the response and COLLECT the fileset object IDs from the returned array (data[].filesetSummary.slaAssignable.id),
             then ADD them to the list of filesets to assign (Step 8 builds the call groups from this list, Step 9 sends it),
             next to the filesets of the hosts that already had the template. No lookups. The IDs are not tied to a host in the
             response, so the host is named only when exactly one host was in the call, otherwise the filesets show as
             "(new on <cluster>)"
             IF the number of IDs differs from the number of hosts sent (normally fewer): PRINT a WARNING and mark those hosts unverified
    IF -recheckFilesetIDs: instead LOOK UP each of those hosts again (one lookup per host) and take its new filesets from the lookup.
             A host where no fileset appears is recorded TemplateFailed

STEP 8   CREATE the Apply CSV (every fileset in the list, old and new, with its starting SLA, status Pending) before any SLA call
         DECIDE again for every fileset in the list (new ones included), collapse duplicate object IDs, then BUILD call groups:
    Bulk (default): batches of up to -batchSize (default 50) fileset object IDs
    Single:         one group per host
STEP 9   FOR EACH group: SEND the assignment mutation (assignSla by default) with that group's fileset object IDs
    ON failure: mark the group CallFailed and continue with the next group
    ON success: mark the filesets Submitted

STEP 10  IF not -skipPolling: POLL every -pollIntervalSec until all Submitted filesets show the SLA (Applied) or -timeoutSec is reached (Timeout)
         ELSE the filesets stay Submitted and nothing is polled
STEP 11  REWRITE the Apply CSV with each fileset's outcome and its host's status (plus one row per host the template could not be
         applied to, and one per host skipped for not being in the inventory)
    IF the hosts came from -filesetCsvPath: WRITE each host's outcome into the CSV's "executed" column (keep a .bak)
    PRINT a note for filesets skipped for a pending SLA, and a warning for hosts skipped for not being in the inventory
    EXIT 1 if any fileset is CallFailed, Timeout, NotAttempted or TemplateFailed (or the apply stopped with an error), otherwise EXIT 0
         (a skip, for a pending SLA or a host not in the inventory, does not by itself change the exit code,
          unless every listed host was skipped, which exits 1)

3. Detailed Steps & GraphQL Reference

Each step corresponds to a function or logic block in Set-SLA-SQL-Fileset.ps1. Every GraphQL call is a POST to <base URL>/api/graphql with the body { "query": ..., "variables": ... }. The Variables blocks show the full variables object the script sends.

REST

0Authenticate to RSC

The script reads the RSC Service Account JSON (-RscServiceAccountJson), confirms it contains client_id, client_secret and access_token_uri, and exchanges them for a bearer token. It requires PowerShell 7+. This is the same block as computer/Core/RSC-Authentication.ps1, copied inline.

MethodPOST
URL<access_token_uri from the service account JSON>

Request body

{
  "grant_type": "client_credentials",
  "client_id": "<from service account JSON>",
  "client_secret": "<from service account JSON>"
}

The tenant base URL is access_token_uri with /api/client_token removed. Every later call is a GraphQL POST to <base URL>/api/graphql with an Authorization: Bearer <access_token> header. The service account needs permission to view hosts and filesets, view SLA Domains, and assign SLAs.

Query

1Resolve -clusterName to a cluster ID (required)

Function: Get-ClusterIdByName

Fileset runs work on one cluster. The same template name can exist on several clusters, so -clusterName is required and limits the template lookup (Step 3), the host lookup (Step 4) and the template application (Step 7) to that cluster. The name is looked up once at the start (before the SLA name is resolved in Step 2) and turned into an ID, because the lookups filter by CLUSTER_ID. The run stops before any change if no cluster, or more than one cluster, has that exact name. It is required for fileset runs (Apply, Test and -getFilesetInventory) and is rejected for SQL. Without it the script stops with "Fileset runs need -clusterName...". The inventory run exits before this lookup (see step I1 in section 4).

query ClusterByNameQuery($filter: ClusterFilterInput) {
  allClusterConnection(filter: $filter, sortBy: ClusterName, sortOrder: ASC) {
    nodes {
      id
      name
    }
  }
}

Variables

{
  "filter": { "name": ["vault-r-madison"] }
}

A host that is on a different cluster is not found by the Step 4 lookup, so it is reported as an error before anything changes. Run once per cluster.

Local logic

5Decide what is skipped

No API call. Every fileset already carries its SLA state from the lookup in the previous step: its assignment type, its effective SLA, and any pending SLA (live from RSC, or from the inventory CSV). The script uses that to decide, for each fileset, whether to assign the target SLA or leave it. Three things are skipped, and the plan, the console and the Apply CSV say which and why:

SkippedWhenWhere it shows
Host not foundWith an inventory, a listed host that is not in the inventory CSV for the -clusterName cluster (including a host the inventory has only on another cluster). (In a live run a host that is not found stops the run instead, before any change.)Plan, end-of-run warning, a NotInInventory row in the Apply CSV
Pending SLAThe fileset has any pending SLA. An assignment is already in flight, and sending another would only queue a second pending action.Plan action Skip: pending, status SkippedPending, a note at the end of the run
Already on the targetThe fileset's effective SLA is already the target, whether it was assigned directly or inherited. Plan action Skip: on target, status AlreadyOnTarget

How "already on the target" is checked, by target:

TargetAlready on target when
An SLA DomaineffectiveSlaDomain.id equals the SLA ID
DO_NOT_PROTECTeffectiveSlaDomain.id == "DO_NOT_PROTECT"
NO_ASSIGNMENTslaAssignment is not "Direct", so the fileset already inherits
  • The pending SLA is checked first, so a fileset with a different SLA pending is skipped too. Rerun once it has finished.
  • A fileset that is on the target by inheritance is skipped, so no direct assignment is added on top of it.
  • With -inventoryCsv the state comes from the saved columns slaAssignment, effectiveSlaId and pendingSlaId, with no RSC call. An inventory written before the pending columns existed has none, so every fileset reads as having nothing pending. Create a new inventory to get the pending check from a file.
  • Filesets created in Step 7 are not in the lookup. Their IDs come from the template call (or, with -recheckFilesetIDs, from a per-host lookup that returns their state). They have no pending SLA and no SLA, so they are always assigned. They are not counted in the plan, which covers only the filesets that already existed.
  • The completion polling in Step 10 asks a different question: whether the assignment has finished, where a pending SLA does mean "not yet". It uses its own query, shown there.
Local logic

6Plan and confirm

No API call. The script prints the plan: a few summary lines (source, workload, mutation, target SLA, apply mode, whether it will poll, the template, how many hosts already have it and how many need it applied, how many filesets exist, how many will be assigned, are already on the target or are skipped for a pending SLA, the template applications, everything that will be skipped and why, and the number of calls), then a table with one row per fileset. The columns are hostName, cluster, object, action, currentSla, pendingSla and assignment. The action is one of:

actionMeaning
AssignThe target SLA will be sent
Skip: on targetThe effective SLA is already the target
Skip: pendingAn SLA is already pending on it, so nothing is sent
Apply templateThe host has no fileset from the template. The template is applied to it, then the new fileset gets the SLA

The cluster column shows the cluster each fileset is on (the -clusterName cluster). The plan's API calls to assign line counts only the calls for the filesets that already exist; it ends with "(plus any for the new filesets)".

  • -dryRun stops here, nothing changes.
  • The script asks you to type YES before it changes anything. Anything other than exactly YES (case-sensitive) cancels and writes nothing. If there is nothing to do (every fileset is already on the target or skipped, and no host needs the template), there is nothing to confirm and no calls are made.
  • To skip the prompt and just run it, add -skipConfirm. The plan is still printed and the Apply CSV is still written before the SLA calls. Only the question is skipped, so use it for a run you have already previewed with -dryRun, or for an unattended run. It applies to -action Apply.
  • The Apply CSV is created later, in Step 8, after any template has been applied and before the first SLA call. A -dryRun or a cancelled run writes no file.

  • Default: no lookups after the call. The new filesets appear in the Apply CSV with the template name as the object, Unassigned as beforeAssignment and an empty beforeSla.   • -recheckFilesetIDs (optional): after the call the script looks each of those hosts up again, one host at a time, and takes the fileset whose template matches. That names the host for every new fileset and reads its state. A host that shows no fileset is recorded as TemplateFailed.

  • If the number of IDs that come back differs from the number of hosts sent (normally fewer), the script prints a warning and treats those hosts as unverified. Use -recheckFilesetIDs to confirm each host. The IDs that did come back are still assigned.
  • The template stays applied to the host afterwards. The script never undoes it, and a rerun treats that host as already having it.
Local logic

8Create the Apply CSV and build the call groups

No API call. First the Apply CSV is created, with one row per fileset in the list (existing and new, including the ones that will be skipped), its starting assignment and SLA, and status Pending. This is the rollback record, and it is rewritten with the results at the end (Step 11). It is written after the template has been applied (Step 7) and before the first SLA call, so a run interrupted during Step 7 has no Apply CSV. The script never reverts anything itself.

Then the filesets that still need the SLA are split into groups, and one assignment call is sent per group.

-applyModeGroupsExample: 120 filesets on 6 hosts, all on the -clusterName cluster
Bulk (default)The filesets are split into batches of up to -batchSize fileset object IDs (default 50).3 calls: 50, 50 and 20 filesets
SingleOne group per host, holding all of that host's filesets (new filesets shown as (new on <cluster>) are not tied to a host, so they go together in one group)6 calls, one per host

The plan's call count uses the same grouping, but only for the filesets that already exist, so it leaves out the calls for filesets the template creates (the plan says "plus any for the new filesets").

Where the fileset object IDs come from. The IDs sent in each call are the IDs of the filesets on each host (the template applied to that host), not the template ID. They are gathered before this step, from two sources, and joined into one list. Everything is on the one cluster given by -clusterName:

HostsWhere their fileset object IDs come from
Hosts that already had the fileset templateThe Get Inventory step (Step 4): the live host lookup, or the inventory CSV. Nothing else is needed.
Hosts the template was just applied to (Step 7)By default, the object IDs returned by the template-application call (data[].filesetSummary.slaAssignable.id), added as they are with no lookups. With -recheckFilesetIDs, a per-host lookup after the call instead.
  • The returned IDs are not tied to a host in the response, which is fine: each is a fileset on the cluster that needs the SLA.
  • The two sets are added together before the call groups are built, so one batch can hold a mix of existing filesets and newly created ones.
  • If the template call failed, those hosts are recorded as TemplateFailed and contribute no ID, so they are left out of every call.
  • In the host CSV, a host that had the template applied and whose filesets reached the target gets TemplateApplied+Assigned, or TemplateApplied+Assigned (unverified, fewer fileset IDs than hosts, use -recheckFilesetIDs) when the ID count did not match. When the IDs are not tied to a host, the hosts in the call share one result (see Step 11).
  • The new filesets have no SLA and nothing pending, so the skip decision (Step 5) always assigns them.
  • The skip decision is made again here for every fileset in the list. An object ID that appears twice is sent once, because the same ID twice in one call can fail the whole call. Every object must have a cluster ID, otherwise the run stops before any call.

Calls are sent one after the other. A failed call marks only that group CallFailed; the remaining groups still run.

10Poll until RSC shows the SLA

Function: Wait-SlaEffectiveWithProgress (skipped with -skipPolling)

The assignment mutation is asynchronous. success: true only means RSC accepted the request; the new SLA first appears as pendingSla and the effective SLA changes later. The script polls the filesets it submitted, with the batched query shown below, every -pollIntervalSec seconds (default 5), until each one is effective or -timeoutSec (default 600) runs out in total.

  • Each poll sends one batched query for only the filesets still waiting (shown below).
  • It prints a progress line each time, for example 12/40 effective, 95s elapsed.
  • A failed poll is reported and retried at the next interval; it does not stop the run.
  • A fileset is effective only when nothing is pending and: for an SLA Domain, it is assigned directly (slaAssignment is Direct) and its effective SLA ID equals the target; for DO_NOT_PROTECT, it is assigned directly and its effective SLA ID is DO_NOT_PROTECT; for NO_ASSIGNMENT, it is not assigned directly. Effective ones become Applied, the rest Timeout. If no call was accepted there is nothing to poll.

Each poll asks for many objects at once using GraphQL aliases (o0, o1, ...), at most 50 per request, so the query text and the variable names grow with the number of objects. It returns each object's assignment type, effective SLA and any pending SLA. The Windows and Linux filesets both support these fields.

query PendingSlaBatchQuery($id0: UUID!, $id1: UUID!) {
  o0: hierarchyObject(fid: $id0) {
    id
    slaAssignment
    effectiveSlaDomain { id name }
    ... on CdmHierarchyObject { pendingSla { id name } }
  }
  o1: hierarchyObject(fid: $id1) {
    id
    slaAssignment
    effectiveSlaDomain { id name }
    ... on CdmHierarchyObject { pendingSla { id name } }
  }
}

Output

11The Apply CSV, host status, and exit code

Each Apply run writes one CSV, <prefix>fileset_sla_apply-<timestamp>.csv. The timestamp includes seconds, so two runs never share a file. The file is written twice:

  • Before the first SLA call, after any template has been applied (Step 8), with one row per fileset: its starting assignment and SLA, and status Pending. If the run is interrupted during the SLA calls, this file still holds the starting state, so it is the rollback record. The script never reverts anything itself.
  • At the end, rewritten with each fileset's outcome and the status of its host. A host with no fileset to show, such as one that is not in the inventory, gets a row with no object.

The file is written to a temporary file and moved into place, so a failure part way cannot leave a half-written CSV. A -dryRun, or answering anything other than YES, writes no file.

Columns: workload, host, cluster, hostStatus, object, objectId, beforeAssignment, beforeSla, beforeSlaId, beforePendingSla, targetSla, assignMutation, applyMode, callGroup, callSec, effectiveSec, status, error. The before* columns are the starting state, callGroup and callSec say which call carried the fileset and how long it took, and effectiveSec is how long after the first call RSC showed the SLA. cluster is the fileset's cluster (empty on rows for a host with no object). A fileset the template just created has the template name in object, Unassigned in beforeAssignment and an empty beforeSla. If every listed host is missing from the inventory CSV, the file written has only the columns workload, host, object, objectId, hostStatus, status, error.

status is per fileset:

SkippedPendingAn SLA was already pending on it, so nothing was sent. Rerun once the pending SLA has finished0

The host CSV's executed column also records TemplateApplied+Assigned for a host that did not have the template, got it applied, and then had every fileset reach the target SLA. With -skipPolling the calls are only submitted, so a host whose calls were accepted is recorded the same way (Assigned) and its objects show Submitted in the Apply CSV.

Filesets that the template call returned for several hosts are listed under the host (new on <cluster>), which is not a real host. Their hostStatus in the Apply CSV is empty. Their combined outcome is given to each host in that template call that has no row of its own, with templateApplied true. In that case the result is the same for all of those hosts, and it is not tied to a particular host.

Exit code: 1 if any fileset is CallFailed, Timeout, NotAttempted or TemplateFailed, or the apply stopped with an error; otherwise 0. A run with no parameters prints a usage summary and exits 0. A run that stops before any change because of an error (for example a host or template not found) assigns nothing.

The console prints the same results as counts by status and by host status, lists any fileset that needs attention, and warns about hosts that were skipped for not being in the inventory. If the hosts came from the host CSV, its executed column is updated too (see section 4). A Timeout does not mean the assignment failed, only that it was not visible in time, so check those filesets in RSC.

With -recheckFilesetIDs the per-host lookups in Step 7 read RSC too. If the inventory is stale, a skip or an assignment can be based on an old SLA or a missing pending SLA, so refresh it when SLAs may have changed.
  • The template is matched in the CSV's Template rows by -filesetName (exact) or -filesetTemplateId. If it is not there, the run stops and tells you to check the name or rerun the inventory. Each host uses the template row on its cluster.
  • -clusterName is still required and the cluster is still looked up, but the CSV is not filtered by it: hosts, clusters and template IDs come from the CSV. Use an inventory for the same cluster.
  • The file must be a fileset inventory with the expected columns, otherwise the run stops with a message saying which column or workload is wrong.
  • The script prints when the inventory was collected and warns if it is older than -inventoryMaxAgeHours (default 24).
  • A host that is in the inventory but has no fileset from the template gets the template applied first (Step 7), and then the SLA is assigned to the full list, new filesets included.
  • A listed host that is not in the inventory at all is skipped. The script prints a warning at the start and again at the end, and writes a NotInInventory row for it in the Apply CSV (and Skipped: not in inventory in the host CSV). The rest of the list still runs. If every listed host is missing, nothing is assigned, the Apply CSV is still written (with only the columns workload, host, object, objectId, hostStatus, status, error), and the script exits 1.
  • With no host list, every host in the inventory on the -clusterName cluster is used, so every host without the template gets it applied.
  • Hosts on another cluster are not used. The saved clusterId of each host is compared with the -clusterName cluster. If the inventory has hosts on other clusters the script prints a warning and leaves them out, and a listed host that is in the inventory only on another cluster is skipped like a host that is not in the inventory (a NotInInventory row, Skipped: not in inventory in the host CSV, and a console line that says it is on a different cluster). This keeps an inventory taken on the wrong cluster from putting an SLA on another cluster's hosts.
  • Used with Apply only: -action Test needs live data, and -inventoryCsv is rejected there.

Filesets and hosts added after the inventory was taken are not in the CSV, so a new host is skipped (and logged) until the inventory is refreshed. Rerun the inventory after onboarding hosts or applying templates.

Handling the inventory file: it lists host names, fileset names, paths and IDs for your environment. Keep it out of any committed folder.

ObjectBehavior
HostNever added. It must already be in Rubrik. In a live run a host that is not found stops the run. In an inventory run a listed host that is not in the inventory is skipped and logged.
Fileset templateNever created, edited or deleted. It must already exist. A template that is not found stops the run.

Existing snapshotsRetained, including when the target is DO_NOT_PROTECT.

Because applying the template is the only addition to a host, run -dryRun first. It lists exactly which hosts would get the template (Apply template) and which already have it.

Parameter rules the script enforces:

  • -RscServiceAccountJson is required. -action must be Apply or Test unless -getSqlInventory or -getFilesetInventory is used (not both).
  • Fileset runs: -clusterName is required; give -filesetName or -filesetTemplateId (not both); give hosts with -filesetHosts or -filesetCsvPath (not needed with -inventoryCsv); give -slaName or -slaID (not both).   • Apply rejects -mode and -setHostLogRetention. -batchSize, -pollIntervalSec and -inventoryMaxAgeHours must be 1 or more.
  • -recheckFilesetIDs is Apply only, fileset only. It is rejected for SQL, for -action Test and for the inventory switches.
  • -inventoryCsv is for -action Apply only, and the file must exist.
