SQL Server Availability Group — SLA Assignment Workflow

Onboarding workflow and script reference for Check-Assign-SLA-SQL-AG.ps1

1. Overall Workflow

When a new Windows SQL Server host is onboarded into Rubrik Security Cloud (RSC), any databases that participate in a SQL Server Availability Group (AG) should be protected at the AG level, not at the individual host/database level. The steps below show where this script fits into the broader onboarding process.

Onboarding steps (outside the scope of this script)
Step A
Add the SQL Host to Rubrik
→
Step B
Wait ~3 minutes for SQL discovery to complete
→
Step C
Assign an SLA at the SQL Host level (protects standalone, non-AG databases)
This script picks up from here
Script Step 1
Check the new SQL Host for databases that are members of an AG
→
Script Step 2
Gather the distinct list of AGs that don't have an SLA assigned yet
→
Script Step 3
Assign the specified SLA Domain to each AG (if one was provided)
Why this matters: An AG-aware SLA assignment protects the AG as a single logical object. Assigning SLA at the host or per-database level instead can result in inconsistent snapshot behavior across AG replicas, or duplicate/competing protection policies on the same data.

2. Script Logic (Pseudocode)

INPUT: one or more SQL host names, optional SLA name or SLA ID, optional -ForceSLA switch

AUTHENTICATE to RSC using the Service Account JSON (client_id/client_secret -> bearer token)

IF an SLA was provided:
    RESOLVE the SLA name to its SLA ID (skip lookup if -SLAId was given directly)

FOR EACH SQL host name provided:
    LOOK UP the host object in RSC by name
    IF host not found: report and skip to next host

    GET all database descendants of the host, including:
        - isInAvailabilityGroup flag
        - logicalPath (used to find the parent AG object, if any)
        - effectiveSlaDomain (the DB's current SLA)

    FOR EACH database on the host:
        IF isInAvailabilityGroup == true:
            RECORD the database + its AG name/ID + current SLA in the summary list
            ADD the AG to a deduped map of "distinct AGs found" (keyed by AG ID)

    REPORT how many DBs are in an AG vs. not, for this host

PRINT the summary table (host, database, AG name/ID, current SLA)

IF an SLA was provided:
    PRINT the deduped list of distinct AGs found
    FOR EACH distinct AG:
        IF the AG already has an SLA assigned (not UNPROTECTED/DO_NOT_PROTECT) AND -ForceSLA was NOT passed:
            SKIP this AG (log as skipped)
        ELSE:
            ASSIGN the resolved SLA to the AG object
            LOG success or failure

IF exporting: WRITE the summary list to a timestamped CSV

3. Detailed Steps & GraphQL Reference

Each step below corresponds to a function or logic block in Check-Assign-SLA-SQL-AG.ps1.

REST

0Authenticate to RSC

Before any GraphQL calls can be made, the script exchanges the RSC Service Account's client credentials for a bearer token. This is a plain REST call (not GraphQL).

0a. Read and validate the Service Account JSON file

The script reads the file at $ServiceAccountPath and confirms it contains client_id, client_secret, and access_token_uri. If any are missing, the script throws and stops before making any network call. Example service account file:

{
  "client_id": "client|abcdef1234567890",
  "client_secret": "SuperSecretClientSecretValue",
  "access_token_uri": "https://mycompany.my.rubrik.com/api/client_token",
  "name": "sql-ag-sla-automation",
  "organization_id": "abcd1234-5678-90ab-cdef-1234567890ab"
}

0b. Derive the tenant's base URL

Before calling out, the script strips the literal /api/client_token suffix off access_token_uri to get the tenant's base URL ($rubrikURL). This is done locally and does not require a network call.

rubrikURL = access_token_uri.Replace("/api/client_token", "")
// e.g. "https://mycompany.my.rubrik.com/api/client_token"
//   -> "https://mycompany.my.rubrik.com"

0c. Exchange credentials for a bearer token

MethodPOST
URL<access_token_uri from service account JSON>
{
  "grant_type": "client_credentials",
  "client_id": "<from service account JSON>",
  "client_secret": "<from service account JSON>"
}

This first call is sent with only Content-Type/Accept headers — there is no bearer token yet. The response's access_token, along with $rubrikURL from step 0b, is stored for the rest of the script's run. If the response does not contain an access_token, the script throws and stops.

0d. Build the GraphQL endpoint and headers

The GraphQL endpoint is $rubrikURL/api/graphql. A fresh headers object is then built with the bearer token, and is what every GraphQL call below actually uses (this is a separate header object from the one used for the token POST in step 0c — it did not have an Authorization value to add to).

endpoint = rubrikURL + "/api/graphql"
headers = {
  "Content-Type": "application/json",
  "Accept": "application/json",
  "Authorization": "Bearer <access_token>"
}
Query

1Look up the SQL Host by name

Function: Get-MssqlHost

Finds the RSC object for the given SQL host name, scoped to MSSQL_HOST type objects. The returned id (fid) is used as the anchor for the next step.

query MssqlTopLevelDescendantsQuery($typeFilter: [HierarchyObjectTypeEnum!], $filter: [Filter!]) {
  mssqlTopLevelDescendants(typeFilter: $typeFilter, filter: $filter) {
    edges {
      node {
        id
        name
        objectType
        __typename
      }
      __typename
    }
    __typename
  }
}

Variables:

NameValue
typeFilter["MSSQL_HOST"]
filter[{ "field": "NAME", "texts": ["<SQLHostName>"] }]
Query

2Get the host's databases and AG membership

Function: Get-MssqlHostDatabases

Returns every database descendant of the host object, each with its isInAvailabilityGroup flag, its current effectiveSlaDomain, and its logicalPath — which contains the parent Availability Group object (objectType: MssqlAvailabilityGroup) when the database is an AG member. Results are paginated with first/after (page size 1000).

query MssqlHostHierarchyDatabaseListQuery($id: UUID!, $typeFilter: [HierarchyObjectTypeEnum!], $first: Int, $after: String) {
  hierarchyObject(fid: $id) {
    id
    name
    ... on MssqlHost {
      databaseDescendantConnection: descendantConnection(typeFilter: $typeFilter, first: $first, after: $after) {
        edges {
          node {
            id
            name
            logicalPath {
              fid
              name
              objectType
              __typename
            }
            effectiveSlaDomain {
              id
              name
              __typename
            }
            ... on MssqlDatabase {
              isInAvailabilityGroup
            }
            __typename
          }
          __typename
        }
        pageInfo {
          endCursor
          hasNextPage
          __typename
        }
        __typename
      }
    }
    __typename
  }
}

Variables:

NameValue
id<host fid from Step 1>
typeFilter["Mssql"]
first1000
after<endCursor from previous page, if paginating>
Local logic

3Identify AG databases and build a deduped AG list

No API call — this is client-side logic performed on the results of Step 2:

  • For each database where isInAvailabilityGroup == true, find the entry in its logicalPath with objectType == "MssqlAvailabilityGroup" to get the AG's fid and name.
  • Add a row to the summary list: host name, database name, AG name, AG ID, and the database's current effectiveSlaDomain.
  • Add the AG to a hash map keyed by AG fid so each distinct AG is only recorded (and later assigned) once, regardless of how many member databases reference it.
Query

4Resolve the SLA Domain name to an ID (only if -SLAName was used)

Function: Get-SLADomainByName

Looks up an SLA Domain by exact name to get its ID. Skipped entirely if -SLAId was passed directly instead of -SLAName.

query SLADomainsForNameFilterQuery($filter: [GlobalSlaFilterInput!]) {
  slaDomains(filter: $filter) {
    nodes {
      id
      name
      __typename
    }
    __typename
  }
}

Variables:

NameValue
filter[{ "field": "NAME", "text": "<SLAName>" }]

The script requires an exact, unique name match — it throws an error if zero or more than one SLA Domain matches the given name.

Local logic

5Decide which AGs to assign (skip already-protected AGs)

No API call. For each distinct AG found in Step 3:

  • If the AG's current SLA is anything other than blank, UNPROTECTED, or DO_NOT_PROTECT, the AG is considered already protected.
  • Already-protected AGs are skipped by default.
  • Pass -ForceSLA to override this and assign the given SLA anyway.
Mutation

6Assign the SLA Domain to the Availability Group

Function: Set-SLAForHierarchy

Assigns the resolved SLA Domain to the AG object's hierarchy. Because the AG object itself is the target (not the individual databases), this single mutation call protects the AG and all of its current member databases together.

mutation AssignSlasForSnappableHierarchiesMutation(
  $globalExistingSnapshotRetention: GlobalExistingSnapshotRetention,
  $globalSlaOptionalFid: UUID,
  $globalSlaAssignType: SlaAssignTypeEnum!,
  $objectIds: [UUID!]!,
  $applicableSnappableTypes: [WorkloadLevelHierarchy!],
  $shouldApplyToExistingSnapshots: Boolean,
  $shouldApplyToNonPolicySnapshots: Boolean,
  $userNote: String
) {
  assignSlasForSnappableHierarchies(
    globalExistingSnapshotRetention: $globalExistingSnapshotRetention,
    globalSlaOptionalFid: $globalSlaOptionalFid,
    globalSlaAssignType: $globalSlaAssignType,
    objectIds: $objectIds,
    applicableSnappableTypes: $applicableSnappableTypes,
    shouldApplyToExistingSnapshots: $shouldApplyToExistingSnapshots,
    shouldApplyToNonPolicySnapshots: $shouldApplyToNonPolicySnapshots,
    userNote: $userNote
  ) {
    success
    __typename
  }
}

Variables:

NameValue
objectIds["<AG fid>"]
globalSlaAssignType"protectWithSlaId"
globalSlaOptionalFid"<resolved SLA Domain ID>"
shouldApplyToExistingSnapshotsfalse
shouldApplyToNonPolicySnapshotsfalse
userNote""

Repeated once per distinct AG that was not skipped in Step 5. The mutation's success field determines whether the script reports the assignment as successful or failed.

Output

7Report results

No API call. The script prints, in order:

  • A summary table of every AG-member database found (host, database, AG name/ID, current SLA).
  • The deduped list of distinct AGs found, with each AG's current SLA.
  • The assign/skip result for each AG as SLA assignment is attempted.

If more than one host was checked, or -ExportCsv is passed, the summary table is also written to a timestamped CSV file.

Reference: powershell/RSC/Check-Assign-SLA-SQL-AG.ps1 — requires PowerShell 7+ and an RSC Service Account with permissions to view MSSQL hosts/databases/Availability Groups/SLA Domains and to assign SLA Domains.
