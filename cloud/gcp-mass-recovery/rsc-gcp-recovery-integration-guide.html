1 The recovery flow at a glance

Recovering one or many GCE instances from RSC is a sequence of nine API interactions. Steps 1–3 are one-time per session. Steps 4–7 gather the inputs the recovery mutation requires. Step 8 is the actual recovery. Step 9 reports progress back to the user.

1
Exchange service account credentials for a bearer token
POST to access_token_uri with grant_type: client_credentials
2
Derive the GraphQL endpoint
Strip /api/client_token from the token URI, append /api/graphql
3
List protected GCE instances
GCPInstancesListQuery → gcpNativeGceInstances
4
User multi-selects instances to recover
Client-side only. No API call. Track a set of RSC instance id values.
5
List snapshots for each selected instance and pick one per instance
SnapshotsListSingleQuery → filter to Primary-resident snapshots → apply Latest / Before / After rule. Note that a Rubrik "snapshot" is a backup, not necessarily a GCP snapshot — see section 6.1.
6
User picks a target GCP project
ListGCPProjectsQuery
7
Resolve target infrastructure for that project
GcpCloudAccountInfoQuery + ListGCPRegionsForProjectQuery + ListGCPNetworksQuery, then ListGCPMachineTypeQuery per instance
8
Submit one recovery mutation per instance
ExportGCPInstanceMutation → returns a jobId per instance
9
Poll activity series until every instance reaches a terminal state
EventSeriesListQuery / EventSeriesDetailsQuery
Bulk model

There is no single "recover N instances" mutation. Bulk recovery is implemented client-side as N independent ExportGCPInstanceMutation calls issued in parallel, each returning its own jobId. This is important for error handling: a failure on one instance does not affect the others, so per-instance success/failure must be tracked independently.

2 Authenticating to RSC

2.1 The RSC service account

RSC authentication uses a service account, created by an RSC administrator under Settings → Users & Access → Service Accounts. On creation, RSC issues a one-time JSON download. This JSON is the only credential material the integration needs.

  "client_secret":    "xY9_EXAMPLE_SECRET_VALUE_DO_NOT_USE_zW4",

  "access_token_uri": "https://example-tenant.my.rubrik.com/api/client_token"

FieldRequiredPurpose
client_idYesOAuth2 client identifier. Always prefixed client|.
client_secretYesOAuth2 client secret. Shown once at creation and never retrievable again.
access_token_uriYesTenant-specific token endpoint. This is also the canonical source of the tenant's base URL — do not ask the user to type the RSC URL separately.

Recommended UX

Accept the service account JSON as a file upload or pasted blob and validate that client_id, client_secret, and access_token_uri are all present before attempting authentication. The reference app rejects the file up front and names the missing fields, which is far clearer than surfacing an opaque 400 from the token endpoint.

2.2 Deriving the tenant base URL

Every tenant has its own hostname. Derive it from access_token_uri by stripping the /api/client_token suffix. Never hardcode a hostname.

The ?op= query parameter

The reference app appends ?op={operationName} to the GraphQL URL. This is not required by the API — the operation is resolved from the request body. It exists purely so that operations are distinguishable in browser devtools, proxy logs, and HAR captures, where every GraphQL call would otherwise show as an identical POST /api/graphql. Recommended, but optional.

2.5 Error handling

GraphQL returns HTTP 200 for application-level errors. A response is only successful if both the HTTP status is 2xx and the body contains no errors array.

Pseudocodeauth + transport layer
function authenticate(serviceAccountJson):
    required = ["client_id", "client_secret", "access_token_uri"]
    missing  = required.filter(f => not serviceAccountJson.has(f))
    if missing.isNotEmpty():
        fail("Service account JSON missing: " + missing.join(", "))

    rscBaseUrl = serviceAccountJson.access_token_uri
                    .replaceSuffix("/api/client_token", "")

    response = httpPost(
        url     = serviceAccountJson.access_token_uri,
        headers = { "Content-Type": "application/json",
                    "Accept":       "application/json" },
        body    = { grant_type:    "client_credentials",
                    client_id:     serviceAccountJson.client_id,
                    client_secret: serviceAccountJson.client_secret })

    if not response.ok:
        fail("Token request failed: " + response.status + " " + response.body)

    token = parseJson(response.body).access_token
    if token is null:
        fail("Token response contained no access_token")

    return { token: token, baseUrl: rscBaseUrl }


function gql(operationName, query, variables):
    response = httpPost(
        url     = rscBaseUrl + "/api/graphql?op=" + operationName,
        headers = { "Content-Type":  "application/json",
                    "Accept":        "application/json",
                    "Authorization": "Bearer " + token },
        body    = { operationName: operationName,
                    variables:     variables,
                    query:         query })

    if not response.ok:
        fail("GraphQL HTTP " + response.status)

    payload = parseJson(response.body)

    // GraphQL reports application errors with HTTP 200.
    if payload.errors is present:
        fail(payload.errors[0].message)

    return payload.data
Token lifetime

Tokens are typically valid for 24 hours. For a long-running service, cache the token with its expires_in and re-authenticate proactively before expiry, or reactively on an HTTP 401. Do not re-authenticate on every call.

Browser-based clients: CORS

RSC does not send permissive CORS headers, so direct browser-to-RSC calls from a third-party origin are blocked. Any browser-delivered integration must proxy RSC traffic through its own backend. The reference app works around this for local use with an Electron main-process bridge or a local Python proxy; neither approach is appropriate for a production SaaS product. Make RSC calls server-side. This also keeps the service account secret off the client.

Known limitation — do not copy this verbatim

The reference app requests first: 500 and does not paginate. It is a field tool sized for the environments it was built for. A production integration must implement cursor pagination: add pageInfo { endCursor hasNextPage } to the connection, add an $after: String variable, and loop until hasNextPage is false.

The same cursor pattern is already demonstrated correctly in the snapshot query in section 6 — reuse that loop shape here. Better still, avoid bulk-loading the inventory at all and let the server filter: see section 3.2.

3.2 Searching for specific instances

The reference app fetches the full inventory once and filters it in the browser. That is workable for a single-operator tool, but for a product-scale integration — and for any tenant with thousands of instances — you want the server to do the filtering. The gcpNativeGceInstances connection accepts a gceInstanceFilters argument for exactly this, and it is the fastest way for a user to zero in on the handful of instances they intend to recover.

GCPInstancesSearchQueryfilterable variant
query GCPInstancesSearchQuery(
  $first: Int, $after: String,
  $sortBy: GcpNativeGceInstanceSortFields, $sortOrder: SortOrder,
  $filters: GcpNativeGceInstanceFilters
) {
  gcpNativeGceInstances(
    first: $first, after: $after,
    sortBy: $sortBy, sortOrder: $sortOrder,
    gceInstanceFilters: $filters
  ) {
    edges {
      cursor
      node {
        id nativeId nativeName vpcName region zone machineType isRelic
        gcpProjectDetails { id nativeName nativeId }
        effectiveSlaDomain { id name }
        allOrgs { fullName }
      }
    }
    pageInfo { endCursor hasNextPage }
  }
}
Argument naming

Note the asymmetry: the GraphQL variable is conventionally called $filters, but the argument on the connection is gceInstanceFilters. Getting this wrong produces an "unknown argument" error rather than a silently unfiltered result.

Search by name or ID substring

The single most useful filter. nameOrIdSubstring matches against both the instance name and its native ID, as a case-insensitive substring — so it behaves like the search box in the RSC UI.

Variablesname search · synthetic example
{
  "first":     50,
  "sortBy":    "GCP_INSTANCE_NATIVE_NAME",
  "sortOrder": "ASC",
  "filters": {
    "nameOrIdSubstringFilter": { "nameOrIdSubstring": "web-server" },
    "relicFilter":             { "relic": false }

}

This returns every live instance whose name or native ID contains web-server. Pairing the substring filter with relicFilter is the common case: it excludes instances that have been deleted in GCP, which is usually what a user searching for a recovery target wants. Omit relicFilter entirely to include relics, or set relic: true to search relics exclusively.

Omit rather than null

An unused filter can be sent as null or left out of the object entirely; both are treated as "no restriction". Selection state and search

If your picker is search-driven, remember that a user will typically search, select a few instances, then search again for the next set. Because selection is a set of RSC instance FIDs (section 5) and not a property of the rendered rows, selections survive a change of search terms for free — but you must keep the selected instance objects cached too, since they will no longer be in the current result page when the batch is finally submitted.

4 The GCE instance data model

There is no separate "instance detail" query in this workflow. The inventory query above returns the complete set of attributes the recovery flow consumes; everything else the UI displays is derived client-side from those fields. This section is the authoritative field reference.

4.1 Field reference

The one field that matters most

id is the RSC FID and is the join key across the entire workflow. Snapshot lookup takes it as workloadId. Activity polling takes it as objectFid. Your internal selection state should be keyed on it. Do not substitute nativeId anywhere — it is a GCP identifier and RSC will not resolve it.

4.2 Values derived client-side

Two presentation values in the reference app are computed locally rather than returned by the API. If you want parity with the Rubrik UI, replicate them.

Protection status

RSC does not return a boolean "protected" flag. Protection status is inferred from the SLA Domain name:

Pseudocode
// RSC uses more than one sentinel for "not protected". Check against a set,
// and compare case-insensitively.
NOT_PROTECTED = { "DO_NOT_PROTECT", "UNPROTECTED" }

isProtected(instance) =
    instance.effectiveSlaDomain?.name is present
    and uppercase(instance.effectiveSlaDomain.name) not in NOT_PROTECTED
Do not test only for UNPROTECTED

An object explicitly set to do-not-protect comes back as DO_NOT_PROTECT, not UNPROTECTED. The reference app tests only for UNPROTECTED and therefore mislabels those instances as protected — a known defect in the app, not intended behaviour. Test against both sentinels.

An unprotected instance may still have snapshots (from a previously assigned SLA or from on-demand backups), so do not use protection status to decide whether an instance is recoverable. Recoverability is determined solely by whether it has an eligible snapshot (section 6).

Machine type family

Machine type lists in the target zone can run to hundreds of entries. The reference app groups them by family for the picker:

PseudocodemachineTypeFamily()
function machineTypeFamily(machineType):
    if machineType is empty: return "Other"

    // Match a leading letter, digits, optional trailing letter:
    //   "n2-standard-4"   -> "N2"
    //   "e2-medium"       -> "E2"
    //   "c3d-highmem-16"  -> "C3D"
    //   "n2d-standard-2"  -> "N2D"
    match = regexMatch(machineType, "^([a-z]\d+[a-z]?)", caseInsensitive)

    return match ? uppercase(match.group(1)) : "Other"

Select-all semantics

"Select all" must apply to the filtered result set, not the entire inventory. A user who filters to region = us-central1 and clicks select-all expects those instances and no others. Equally, selections made under one filter must survive a filter change — the selection set is independent of the view. Both behaviours fall out naturally from keeping selection in a set of IDs rather than as a per-row boolean.

5.2 Transitioning into the recovery wizard

When the user initiates recovery, the reference app performs three things before showing target configuration:

  1. Fetches snapshots for every selected instance in parallel and resolves one snapshot per instance according to the active selection mode (section 6).
  2. Identifies instances with no eligible snapshot and explicitly confirms with the user that those will be skipped. It does not silently drop them.
  3. Generates a default target name and default machine type per surviving instance.

function beginRecovery():

Skipped instances are a correctness issue, not a UI nicety

An instance with no Primary-resident snapshot cannot be recovered by this flow. If your tool silently omits it, the user believes they recovered N instances when they recovered N minus the skipped ones. Make the skip explicit and name the instances.

6 Selecting snapshots

Each instance is recovered from exactly one snapshot, resolved independently per instance. Snapshots are queried one instance at a time, keyed on the RSC instance id.

6.1 What "snapshot" means here

A Rubrik snapshot is not a GCP snapshot

The API calls these objects snapshots, but a Rubrik snapshot is a Rubrik backup — a recovery point — not a GCE disk snapshot. It is a logical object that may be materialised as a GCP snapshot, as an immutable object in a Google Cloud Storage bucket, or as both at once. Reading "snapshot" as "GCP snapshot" will lead you to the wrong conclusions about what is recoverable.

When Rubrik protects a GCE instance it takes a GCP snapshot of the instance's disks. What happens to that data afterwards is governed by the SLA Domain assigned to the workload, and it can land in either or both of two tiers:

TierWhere the data livesCharacteristics
Primary
"local"		 A native GCP snapshot, retained in the customer's own GCP project Fastest to recover from and the only tier this export flow can use directly. Incurs ongoing GCP snapshot storage cost, so retention here is often deliberately short.
Archive An object in a Rubrik-managed GCS bucket Can be made immutable for ransomware resilience, and is typically far cheaper for long retention. The bucket may be in a different project and a different region from the source instance.

Crucially, the Primary tier can be configured to retain nothing at all. Because GCP snapshots are expensive, a common cost-optimised policy leaves no GCP snapshots behind and keeps every recovery point in GCS only.

Two representative SLA Domains
SLA "A" - hybrid retention
    Primary (GCP snapshots) :  7 days
    Archive (GCS bucket)    : 30 daily + 12 monthly

SLA "B" - cost-optimised, no GCP snapshots retained
    Primary (GCP snapshots) :  0 days     <-- nothing left behind
    Archive (GCS bucket)    : 30 days

How the tiers appear in the API

Each snapshot node carries its per-tier residency under snapshotRetentionInfo:

FieldTierNotes
localInfo Primary The GCP snapshot. locationName is "Primary" and locationId is "PolarisCluster". isSnapshotPresent tells you whether the GCP snapshot still exists.
archivalInfos[] Archive One entry per GCS archival location, each with its own locationName (the configured archival target's name), locationId (a UUID), expirationTime, and isSnapshotPresent.
Consequence for this integration

The export flow documented in section 8 uses snapshotType: "SOURCE", which requires the Primary copy — the actual GCP snapshot — to still exist. For a workload under an SLA like "B" above, every snapshot will report localInfo.isSnapshotPresent: false, the Primary-residency filter in section 6.3 will match nothing, and the instance will be reported as having no eligible snapshot.

This is expected behaviour, not a bug — but it means a correctly protected, fully recoverable instance can legitimately show up as unrecoverable to this flow. Recovering from a GCS-resident copy is a separate path that this guide does not cover. Surface the distinction to your users rather than reporting "no snapshots", and consider confirming the expected retention policy with the customer when an entire workload comes back empty.

Optional: report archival copies

The reference app requests only localInfo and therefore infers "archival only" from the absence of a Primary copy. If you want to state it positively — "no GCP snapshot; 4 copies in GCS" — add archivalInfos { locationName expirationTime isSnapshotPresent } alongside localInfo in the query in section 6.2. This is an addition to the reference app's selection set, not something it does today.

6.3 The Primary-residency rule

Critical — the most common integration mistake

A snapshot returned by this query is only recoverable via snapshotType: SOURCE if: 

node.snapshotRetentionInfo.localInfo.isSnapshotPresent == true

Snapshots where this is false have no GCP snapshot left — the recovery point exists only as an object in a GCS archival bucket (section 6.1). They are returned by the query and look identical in every other respect, but attempting a SOURCE export against one will fail or require rehydration through a different recovery path. Filter these out before applying any selection logic, and treat an instance whose snapshots are all archival as having no eligible snapshot for this flow.

It is worth surfacing the archival count in the UI rather than hiding it — "no GCP snapshot; 3 copies in GCS" tells the user something actionable, where "no snapshots" does not, and it avoids implying the workload is unprotected when it may be fully protected under a GCS-only retention policy.

6.4 Fetching with pagination

Pseudocodeper-instance snapshot fetch
function loadSnapshotsForInstances(instances):
    // Fetch all instances concurrently - this is the dominant cost of entering
    // the wizard, and it parallelises cleanly.
    parallelForEach(instances, instance => {
        try:
            all         = []
            after       = null
            hasNextPage = true

            while hasNextPage:
                vars = { snappableId:                instance.id,
                         includeOnlySourceSnapshots: true,
                         first:                      200,
                         sortBy:                     "CREATION_TIME",
                         sortOrder:                  "DESC",
                         snapshotFilter: [ { field: "SNAPSHOT_TYPE", typeFilters: [] } ],
                         timeRange:                  null,
                         after:                      after }

                data = gql("SnapshotsListSingleQuery", SNAPSHOTS_QUERY, vars)
                conn = data.snapshotsListConnection

                all.addAll(conn.edges.map(e => e.node))

                hasNextPage = conn.pageInfo.hasNextPage
                after       = conn.pageInfo.endCursor

                // Safety valve: long-retained workloads can have thousands of
                // snapshots. 1000 is far more than any selection rule needs.
                if all.size >= 1000: break

            all.sortDescendingBy(snapshot => parseDate(snapshot.date))
            snapshotCache[instance.id] = all

        catch error:
            snapshotErrors[instance.id] = error.message

        // Resolve the chosen snapshot immediately, per instance.
        resolveSnapshot(instance)
    })

6.5 The selection algorithm

The user picks one selection mode that applies to the whole batch; the rule is then evaluated independently against each instance's own snapshot list. Because snapshot schedules differ per instance, an exact match may not exist for every instance — hence the symmetric fallback.

ModeRuleFallback when no match
latestNewest eligible snapshot.None needed.
beforeNewest snapshot at or before the target timestamp.Oldest snapshot after the target — i.e. the nearest available in the other direction.
afterOldest snapshot at or after the target timestamp.Newest snapshot before the target.
PseudocoderesolveSnapshot()
function resolveSnapshot(instance):
    raw = snapshotCache[instance.id]

    if raw is null or raw.isEmpty():
        selectedSnapshots.remove(instance.id)
        display(instance, "No snapshots")
        return

    // === The Primary-residency filter. Apply before anything else. ===
    eligible = raw.filter(s =>
        s.snapshotRetentionInfo?.localInfo?.isSnapshotPresent == true)

    if eligible.isEmpty():
        archivalCount = raw.size
        selectedSnapshots.remove(instance.id)
        display(instance, "No Primary snapshots (" + archivalCount + " archival only)")
        return

    // eligible is sorted newest-first.
    chosen       = null
    fallbackUsed = null

    if mode == "latest":
        chosen = eligible.first()

    else:
        target = userSelectedTimestampAsUtc()

        if target is null:
            chosen = eligible.first()

        else if mode == "before":
            // Newest snapshot at or before target.
            chosen = eligible.findFirst(s => parseDate(s.date) <= target)

            if chosen is null:
                // Nothing that old exists. Fall back to the OLDEST snapshot
                // after the target - the closest available point in time.
                afters = eligible.filter(s => parseDate(s.date) > target)
                chosen = afters.last() ?? eligible.first()
                if chosen is not null: fallbackUsed = "after"

        else:   // mode == "after"
            afters = eligible.filter(s => parseDate(s.date) >= target)

            if afters.isNotEmpty():
                // afters is newest-first, so last() is the OLDEST snapshot
                // at or after the target - i.e. the closest one.
                chosen = afters.last()
            else:
                // Nothing that recent exists. Fall back to the newest snapshot
                // before the target.
                chosen = eligible.findFirst(s => parseDate(s.date) < target)
                if chosen is not null: fallbackUsed = "before"

    if chosen is null:
        selectedSnapshots.remove(instance.id)
        return

    selectedSnapshots[instance.id] = {
        id:         chosen.id,
        date:       chosen.date,
        type:       "SOURCE",
        isOnDemand: chosen.isOnDemandSnapshot
    }

    if fallbackUsed is not null:
        // Surface this. The user asked for a point in time and is getting a
        // different one; silently substituting is a data-loss surprise.
        warn(instance, "No snapshot " + mode + " the requested time; "
                       + "using nearest " + fallbackUsed)
Always show the resolved timestamp

Because each instance resolves independently, a batch of 20 instances can easily recover from 20 different points in time. The review step must show the actual resolved snapshot timestamp per instance, not just the rule that was requested. The reference app also shows the oldest and newest available snapshot per instance so the user can see the bounds they are working within.

8.3 Friendly names in the UI, identifiers in the payload

This is the single most important structural point about the mutation, and the one most likely to cost development time if it is discovered late.

No value in the mutation can be typed by hand

Every field in GcpNativeExportGceInstanceInput must carry a value that came back from an earlier RSC query response. The user selects a human-friendly name — a project called "example-prod-project", a snapshot dated 23 Sep 2026 — but what the mutation receives is the identifier RSC returned alongside that name. Your picker components must carry both: the friendly label for display, and the underlying value for submission.

The catch is that the required form is not uniform across fields. Three different things happen depending on the field, and treating them all the same way fails in both directions — sending a name where a UUID is expected, or trying to resolve a UUID for a field that wants the plain name.

The three forms

  1. Rubrik FIDs (UUIDs). targetGcpProjectRubrikId and snapshotId. These are RSC's own object identifiers and are meaningless to GCP. They are the classic name-to-ID lookup: the user picks "example-prod-project" and you must submit the UUID RSC returned with it. There is no way to derive one from the name; you must retain it from the query response.
  2. GCP native identifiers. sharedVpcHostProjectNativeId and serviceAccountId. Not Rubrik IDs, but still values you must obtain from RSC rather than construct — RSC is the authority on which service account it will use to perform the recovery.
  3. Plain names, passed through unchanged. targetZone, targetSubnetName, targetMachineType. Do not attempt to resolve these to IDs — RSC expects the literal GCP name string. They must still originate from the corresponding RSC query, though, because RSC validates them against what it can actually reach: a zone or subnet that is real in GCP but not returned by these queries will fail at recovery time.
Practical implication for your picker components

Model every target selector as an object carrying { label, value, source } rather than as a bare string, and populate all of them exclusively from RSC query responses. Never let a user free-type a project, zone, subnet, or machine type. The reference app follows this pattern: its project dropdown displays node.name while carrying node.id, and it keeps the whole project object attached to the option so both id and nativeId are available at submission time.

8.4 Two naming traps

Trap 1 — serviceAccountId is not an ID

The field name strongly implies a Rubrik object identifier or a numeric GCP account ID. It is neither. It carries the service account email address returned verbatim as gcpCloudAccountGetProject.project.effectiveServiceAccount, for example rubrik-recovery@example-prod-project-482910.iam.gserviceaccount.com. Passing any kind of UUID here will fail. Pass the string through unchanged.

Trap 2 — sharedVpcHostProjectNativeId is not only for Shared VPC

The name suggests it should be populated only when deploying into a Shared VPC host project. In practice the reference app always sends the selected target project's nativeId here, Shared VPC or not, and this is the behaviour known to work. Do not conditionally omit it.

8.5 Target instance naming

Recovered instances need names that do not collide with existing instances in the target project. The reference app appends a timestamp derived from the snapshot's own date — which is more useful than the current time, because the name then states what point in time the instance represents.

PseudocodemakeTargetName()
// Produces e.g. "web-server-01-0923-0100"
//   base   = source instance name, lowercased
//   suffix = snapshot date as MMDD-HHMM in the display timezone
function makeTargetName(instance):
    snapshot = selectedSnapshots[instance.id]

    if snapshot is not null and snapshot.date is not null:
        suffix = formatAsMMDD_HHMM(parseDate(snapshot.date), timezone)
    else:
        // Edge case only - a random 5-char token keeps the name unique.
        suffix = randomAlphanumeric(5)

    base = lowercase(instance.nativeName ?? "vm")
    name = base + "-" + suffix

    // GCP caps instance names at 63 characters. Truncate the BASE, never the
    // suffix, and never leave a trailing hyphen.
    if name.length > 63:
        maxBase = 63 - (suffix.length + 1)
        base    = trimTrailingHyphens(base.substring(0, maxBase))
        name    = base + "-" + suffix

    return name
Timezone

The reference app renders all timestamps — including this name suffix — in US Central Time, because that is what its users expect. For a multi-tenant product, use the viewing user's timezone or UTC, but be consistent: the suffix in the instance name and the snapshot time shown in the review screen must agree, or users will believe they recovered the wrong point in time.

8.6 Submitting the batch

Pseudocodebulk submission
function startRecovery():
    instances   = selectedInstances.filter(i => selectedSnapshots[i.id] is not null)
    submittedAt = now()

    // Create tracking entries BEFORE submitting, so the progress view can be
    // shown immediately rather than after the last request returns.
    for instance in instances:
        jobs[instance.id] = {
            instanceId:  instance.id,
            instanceName: instance.nativeName,
            targetName:  perInstanceConfig[instance.id].targetName,
            jobId:       null,
            status:      "Submitting",
            message:     "Sending recovery request to RSC...",
            submittedAt: submittedAt,
            error:       null
        }

    showProgressView(jobs)

    // Submit all instances concurrently. Each is independent; one failure
    // must not abort the others.
    parallelForEach(instances, instance => {
        entry    = jobs[instance.id]
        snapshot = selectedSnapshots[instance.id]

        try:
            input = {
                snapshotId:                   snapshot.id,
                snapshotType:                 snapshot.type ?? "SOURCE",

                targetGcpProjectRubrikId:     settings.targetProjectRubrikId,
                sharedVpcHostProjectNativeId: settings.targetProjectNativeId,
                targetZone:                   settings.zone,

                targetInstanceName:           entry.targetName,
                targetMachineType:            perInstanceConfig[instance.id].machineType,
                targetSubnetName:             settings.subnet ?? "default",
                targetNetworkTags:            settings.networkTags,

                serviceAccountId:             settings.serviceAccountEmail,

                diskEncryptionType:           settings.encryption,
                kmsCryptoKey:                 settings.encryption == "CUSTOMER_MANAGED_KEY"
                                                  ? settings.kmsKey : null,
                kmsCryptoKeyResourceId:       null,

                shouldCopyLabels:             settings.copyLabels,
                shouldAddRubrikLabels:        settings.addRubrikLabels,
                shouldPowerOff:               settings.launchStopped
            }

            data = gql("ExportGCPInstanceMutation", EXPORT_MUTATION, { input: input })

            entry.jobId   = data.gcpNativeExportGceInstance.jobId
            entry.status  = "Pending"
            entry.message = "Waiting for RSC to register activity..."

        catch error:
            // Isolate the failure to this instance only.
            entry.status  = "Failure"
            entry.error   = error.message
            entry.message = "Submission failed: " + error.message

        refreshProgressView()
    })

    // Activity series take a moment to appear after submission.
    scheduleAfter(2 seconds, () => pollProgress())
Keep the returned jobId

The jobId is the identifier of the activity series RSC creates for this recovery. Store it per instance — it lets you query that instance's progress directly, without any correlation logic. See section 9.2.

9.2 Correlating activities back to submissions

The jobId is the activitySeriesId

The value ExportGCPInstanceMutation returns as jobId is the same value the activity series reports as activitySeriesId. Verified against a live capture: a mutation returning jobId: "7f2e4a91-3c6d-4b85-9a10-2d5e8f014c73" produced an activity series with activitySeriesId: "7f2e4a91-3c6d-4b85-9a10-2d5e8f014c73". Track by that value and no correlation logic is needed at all.

This gives you two ways to poll, and you should generally prefer the first:

function pollProgress():
    parallelForEach(jobs.values(), entry => {
        if entry.jobId is null: return      // submission failed; nothing to poll

        // The jobId IS the activity series id. No lookup, no correlation.
        series = fetchActivitySeriesDetails(
                     activitySeriesId = entry.jobId,
                     clusterUuid      = "00000000-0000-0000-0000-000000000000")

        entry.status        = series.lastActivityStatus
        entry.progress      = series.progress
        entry.lastEventTime = series.lastUpdated
        entry.events        = series.activityConnection.nodes   // full timeline
        entry.message       = series.activityConnection.nodes.first()?.message
    })

    if jobs.values().anyMatch(j => not isTerminal(j.status)):
        scheduleAfter(10 seconds, pollProgress)
    else:
        markAllComplete()


function isTerminal(status):
    if status is empty: return false
    s = lowercase(status)
    return s in ["success", "failure", "canceled", "tasksuccess", "taskfailure"]

Batch polling by instance FID

One EventSeriesListQuery can cover the whole batch, which is cheaper than N detail calls when you only need status and not the full timeline. The cost is that series are keyed on objectId (the instance FID), so an instance recovered more than once yields multiple matching series. With the jobId in hand you can disambiguate exactly; the reference app, which does not use the jobId, falls back to matching on submission time.

Pseudocodebatch polling
function pollProgressBatch():
    earliest   = min(jobs.values().map(j => j.submittedAt))
    lowerBound = earliest - 10 seconds

    series = fetchActivitySeries({
        objectFid:         jobs.keys().distinct(),
        lastActivityTypes: ["RECOVERY", "BULK_RECOVERY"],
        lastUpdatedTimeGt: lowerBound.toIso8601()
    })

    for entry in jobs.values():
        // Exact match when we kept the jobId ...
        match = series.findFirst(s => s.activitySeriesId == entry.jobId)

        // ... otherwise fall back to time-based matching (reference app behaviour).
        if match is null:
            candidates = series.filter(s => s.objectId == entry.instanceId)
            if candidates.isEmpty(): continue          // not registered yet
            candidates.sortAscendingBy(s => parseDate(s.lastUpdated))
            match = candidates.findFirst(c =>
                        parseDate(c.lastUpdated) >= entry.submittedAt - 5 seconds)
                    ?? candidates.last()

        entry.activitySeriesId = match.activitySeriesId
        entry.clusterUuid      = match.clusterUuid
        entry.status           = match.lastActivityStatus
        entry.message          = match.latestMessage ?? entry.message
        entry.progress         = match.progress ?? entry.progress
        entry.lastEventTime    = match.lastUpdated

Implementation checklist

  • Make all RSC calls server-side. Never ship the service account secret to a browser.
  • Cache the bearer token; re-authenticate on expiry or on HTTP 401, not per request.
  • Treat HTTP 200 with an errors array as a failure.
  • Paginate the inventory query. The reference app does not, and that is a known limitation.
  • Filter server-side with gceInstanceFilters rather than bulk-loading and filtering locally. Build the filter object from only the criteria the user set; omit the rest.
  • Filter snapshots on isSnapshotPresent == true before applying any selection rule.
  • Tell the user explicitly which instances are being skipped for lack of an eligible snapshot.
  • Show the resolved snapshot timestamp per instance, not just the selection rule.
  • Pass the service account email as serviceAccountId.
  • Always send sharedVpcHostProjectNativeId, Shared VPC or not.
  • Validate target instance names against GCP rules: lowercase, digits, hyphens, 63 chars, no trailing hyphen.
  • Submit one mutation per instance, in parallel, with per-instance failure isolation.
  • Keep the jobId from each mutation — it is the activitySeriesId, so progress needs no correlation logic.
  • Treat both DO_NOT_PROTECT and UNPROTECTED as "not protected".
  • Remember that filter enums are SCREAMING_SNAKE_CASE but response enums are PascalCase.
  • Compare activity statuses case-insensitively and stop polling on terminal states.
