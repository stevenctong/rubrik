Rubrik · Field Runbook

Azure VHD Mass Recovery

Recover VMware VMs from Rubrik into Azure as native VMs, rebuild in-guest drive layout, then restore application data by file-level recovery or MSSQL export. Every stage is driven by CSV columns you fill in.

Scope cloud/azurevhd Phases 3 Scripts 11 Audience Field SE / operator

Overview

Three phases, run in order. Each has its own orchestrator, its own state file, and its own resume behavior.

PhaseWhat it doesWhere it runs
1 · Conversion Download VMDKs from Rubrik, convert to fixed VHD, upload to Azure as managed disks, create the VM Staging Windows host with the Hyper-V role
2 · Drive rebuild Recreate partitions, file systems, labels and drive letters on the raw disks Source VM to capture, then target Azure VM to apply
3 · Data recovery Restore application data by file-level recovery or MSSQL bulk export Any host with RSC access

Phase 3 branches. A given server goes down the FLR path, the SQL path, or both. The branch is selected purely by which CSV columns you fill in — there is no flag or switch.

There are two CSVs, not one

This is the single most common point of confusion. They come from different scripts, have different schemas, and are read by different phases.

CSV 1 · master control file
rubrik_vm_list-<timestamp>.csv

Produced by Get-RubrikVMDKList.ps1. One row per VMDK, so a four-disk VM produces four rows. Drives Phase 1 and Phase 3. 36 columns, roughly 22 of them yours to fill.

CSV 2 · per-server disk capture
drive_info-<COMPUTERNAME>.csv

Produced by Get-DriveInfo.ps1 on the source VM before migration. One row per lettered volume. Drives Phase 2 only. 17 columns, all auto-captured.

Timing

CSV 2 must be captured while the source VM is still running. Once the VM is gone the information cannot be recovered from Azure, because the raw managed disks carry no partition table. Save it somewhere outside the VM.

1 Conversion

VMware to Azure conversion

Takes VMDKs from a Rubrik snapshot and produces a running Azure VM with all disks attached. Runs on a staging Windows host with the Hyper-V role installed.

Runbook steps

Step 1 — Generate the CSV

./Get-RubrikVMDKList.ps1 -RscServiceAccountJson './rsc-service-account.json'

# Only VMs with snapshots on one cluster
./Get-RubrikVMDKList.ps1 -RscServiceAccountJson './rsc.json' -RecoveryCluster 'vault-r-madison'

# Fresh CSV, discard prior edits
./Get-RubrikVMDKList.ps1 -RscServiceAccountJson './rsc.json' -SkipMerge

Output is ./rubrik_vm_list-<yyyy-MM-dd_HHmm>.csv, covering both primary and replica objects. Only VMs with at least one snapshot appear.

Step 2 — Fill in the CSV

Per VMDK row, pick an action:

GoalMark
Transfer this disk's data to AzureConvert = x
Create an empty disk of the same size, repopulate later via Phase 3CreateOnly = x
Ignore this diskleave both blank

Per VM, mark exactly one row BootDisk = x. That row is also where the per-VM Azure settings are read from, so put ResourceGroup, VNetRG, VNetName, SubnetName and VMSize on it.

Why CreateOnly exists

For data volumes where you want the disk present and correctly sized in Azure but intend to repopulate the contents via Phase 3 rather than transferring the full VMDK. It skips download, conversion and upload entirely, which is the difference between minutes and hours on a large data volume.

Step 3 — Configure the pipeline

# conversion_config.psd1
@{
    RscServiceAccountJson = './rsc-service-account-rr.json'
    workingDir            = 'F:\conversions'
    throttleLimit         = 5
    aria2cPath            = 'F:\aria2\aria2c.exe'
    qemuPath              = 'C:\Program Files\qemu\qemu-img.exe'
    azcopyPath            = 'F:\azcopy\azcopy.exe'
    timeoutMinutes        = 60

    RunDownload = $true
    RunConvert  = $true
    RunUpload   = $true

    subscription = 'RR-PRD'
    location     = 'eastus2'
    osType       = 'Windows'
    skuName      = 'StandardSSD_LRS'

    useStorageAccount    = $false
    storageAccountName   = 'rrtonglighthouse101'
    storageContainerName = 'vhds'
    storageAccountRG     = 'rr-tong'
}

vmCsvFile is commented out in the shipped config. Either uncomment it or pass -vmCsvFile. Command-line parameters override config file values.

Step 4 — Run

./Start-VMConversion.ps1 -pipelineConfig './conversion_config.psd1' `
  -vmCsvFile './rubrik_vm_list-2026-08-18_1317.csv'

# Test download and convert without touching Azure
./Start-VMConversion.ps1 -pipelineConfig './conversion_config.psd1' -RunUpload $false

# Retry VMs that failed on a prior run
./Start-VMConversion.ps1 -pipelineConfig './conversion_config.psd1' -RetryFailed

Pre-flight checks before any work starts

  1. PowerShell 7+ present
  2. RSC JSON, CSV, aria2c, qemu-img and azcopy all exist, for enabled stages only
  3. No row has both Convert and CreateOnly — hard error
  4. No CreateOnly row is also BootDisk — hard error
  5. At least one actionable row exists
  6. Disk space summary against the estimate — warning only, does not block
  7. Per-VM required Azure columns present — hard error, listed per VM
  8. Connect-AzAccount against the configured subscription

What each stage does

Stage 1 — Download

Two paths. It first looks for a successful Recovery event on this VM in the last 24 hours and scrapes download links from the event messages. If every requested VMDK is covered, it reuses those links and skips the export entirely.

Otherwise it fires downloadVsphereVirtualMachineFiles, waits 15 seconds, finds the matching recovery event, and polls every 60 seconds until SUCCESS. Then it opens a CDM session directly against the cluster and pulls each URL with aria2c. Both the .vmdk descriptor and the -flat.vmdk data file land in the download directory.

Timeout behavior

timeoutMinutes (default 60) applies only to the export preparation poll, not to the transfer. The transfer has no wall-clock limit. Instead it polls file size every 30 seconds, and if the size is unchanged for three consecutive polls (90 seconds) it kills aria2c, deletes the partial file, and restarts. Up to three attempts per URL.

A non-zero aria2c exit code is not retried. Only stalls are.

Stage 2 — Convert

For each .vmdk descriptor in the download directory:

  1. Rewrite the descriptor in place. Every RW <n> VMFS extent line becomes RW <n> FLAT, because qemu-img cannot read the VMFS extent type Rubrik exports. Note this mutates the downloaded file, it is not a copy.
  2. Detect partition style and boot disk by reading the first 2048 bytes of the flat file. EFI PART at offset 512 means GPT, then it scans the first eight GPT entries for the EFI System Partition type GUID. Otherwise 0x55AA at offset 510 means MBR, then it checks the four primary entries for the 0x80 active flag.
  3. Size gate. Anything over 2 TiB is skipped with a warning and produces no report entry.
  4. Convert: qemu-img convert -f vmdk -O vpc -o subformat=fixed
  5. Clear the NTFS sparse flag. Windows can mark the qemu output sparse, which breaks the fully-allocated guarantee Azure requires.
  6. Align to 1 MB with Resize-VHD. Azure rejects unaligned VHDs on direct upload.

Writes conversion_report.json, an array of successfully converted disks:

[
  {
    "sourceFile":       "vmname.vmdk",
    "targetFile":       "vmname.vhd",
    "partitionStyle":   "GPT",
    "isBootDisk":       true,
    "virtualSizeBytes": 96636764160
  }
]

Skipped and failed disks produce no entry. When exactly one disk converts, PowerShell emits a bare object rather than an array.

Stage 3 — Upload and VM creation

  1. Read conversion_report.json for the boot disk and derive the Hyper-V generation: MBR gives V1, GPT gives V2. Falls back to the CSV BootDisk marking, then to the first converted file with a warning.
  2. Upload the boot disk as a managed disk named {tgtVMName}-{DiskSuffix}.
  3. Upload each remaining VHD as a data disk.
  4. Create empty managed disks for every CreateOnly row, sized from vmdkSizeGiB rounded up.
  5. Create NIC {tgtVMName}-nic-01 with accelerated networking.
  6. Call New-AzVM once with every disk attached. Data disks get sequential LUNs from 0.
  7. Poll power state up to five minutes for VM running.

Resume, retry and idempotency

State lives in <workingDir>\conversion_state.csv, one row per VM keyed on the RSC VM FID, with independent DownloadStatus, ConvertStatus and UploadStatus columns.

Prior stateBehavior on re-run
All three stages CompleteSkipped entirely
Stage = FailedSkipped unless -RetryFailed
Anything elseResumes, running only the incomplete stages

Azure resources are reused rather than recreated when they already exist with the expected name and a ProvisioningState of Succeeded: managed disks, the NIC, and the VM itself. If the target VM already exists and is running, upload is marked complete and skipped. If the VM name is taken in the resource group, the orchestrator prefixes it with az- and continues.

A Partial result means the pipeline finished without error but one or more stages were switched off via the Run* flags.

2 Drive rebuild

In-guest drive rebuild

Recreates the source VM's drive letters, labels, file systems and allocation unit sizes on the raw disks attached to the recovered Azure VM.

CreateOnly disks arrive in Azure raw and uninitialized. Without this step they have no partition table and no drive letters, so a Phase 3 restore has nowhere to land.

Step 1 — Capture on the source VM

# Elevated PowerShell on the SOURCE VM, before migration
./Get-DriveInfo.ps1

# Custom output path
./Get-DriveInfo.ps1 -OutputPath 'C:\temp\drives.csv'

Produces ./drive_info-<COMPUTERNAME>.csv plus a table and warnings on screen.

Read the warnings before you migrate

Dynamic disk — will be skipped by Initialize-VMDrives.ps1. Plan manual configuration.
Multi-partition disk — handled automatically, but verify partition sizes afterwards.
Mount point volume — never written to the CSV at all. Fully manual after migration.

Step 2 — Apply on the target Azure VM

# Always preview first. -WhatIf prints the match plan and exits.
./Initialize-VMDrives.ps1 -CsvFile '.\drive_info-SQLSERVER01.csv' -WhatIf

# Then run for real
./Initialize-VMDrives.ps1 -CsvFile '.\drive_info-SQLSERVER01.csv'

# CSV holds several servers
./Initialize-VMDrives.ps1 -CsvFile '.\drives.csv' -ServerName 'SQLSERVER01'

# Unattended
./Initialize-VMDrives.ps1 -CsvFile '.\drives.csv' -SkipConfirmation

How disks are matched

Matching is by size only

There is no LUN, SCSI target or disk number correlation, even though the CSV carries BusType and ScsiTarget. The source DiskNumber is used only as a grouping key for multi-partition detection — source and target disk numbers need not correspond.

  1. Candidate pool is every disk where PartitionStyle -eq 'RAW'. A disk that is already initialized, even if empty, is invisible to the matcher.
  2. Tolerance is 10 percent of the CSV target size, either direction. Among all disks inside tolerance, the smallest absolute difference wins. This absorbs Azure's fixed disk tiers, since a 500 GiB source volume lands on a 512 GiB managed disk.
  3. Largest first, greedy. Multi-partition groups are matched first by summed capacity descending, then single-partition rows by capacity descending. Each raw disk is consumed once.
  4. Target size used is TotalCapacityMB for a single-partition row, or DiskSizeGB × 1024 for a multi-partition group, falling back to summed volume capacity plus 5 percent.
Same-size disks are ambiguous

If two raw disks are the same size, which one gets which drive letter is effectively arbitrary, determined by CSV row order. The script detects this and warns. It is harmless for empty disks being formatted from scratch, but the disk-number to drive-letter mapping is not reproducible run to run.

Multi-partition disks

Rows are grouped by the source DiskNumber. Partitions are created largest first; every partition except the last is sized to its source volume capacity, and the smallest volume in the group is created last with -UseMaximumSize to absorb leftover space.

One thing to watch: the partition style for the whole physical disk comes from the group's first CSV row in file order, not per row. If rows in a group disagree, the first wins. File system and allocation unit size are applied per row.

What gets skipped

SkippedRule
Existing drive lettersThe letter already exists on the target. This is what makes the script safe to re-run.
Dynamic disksDiskType is Dynamic. Cannot be recreated with Initialize-Disk / New-Partition.
Empty Drive cellSilently skipped.
The boot drive is not explicitly excluded

IsBoot and IsSystem are never read by this script. C: is skipped only incidentally, because it already exists on the target and hits the existing-letter filter. If a CSV row's letter happened not to exist on the target, the script would try to create it regardless of the flag.

Verify after the run

Get-Volume | Sort-Object DriveLetter |
  Format-Table DriveLetter, FileSystemLabel, FileSystem, Size, SizeRemaining

3 Data recovery

FLR and SQL restore

Two independent paths, both driven off the same VM list CSV. Which one runs is decided entirely by which columns you filled in.

Both share the same job key: sourceHostname|targetHost, where targetHost is targetRbsWinHost falling back to tgtVMName.

Common prerequisite

The target Windows host must have Rubrik Backup Service installed and be registered on the same Rubrik cluster as the source. Both scripts constrain the target lookup to the source's cluster ID.

Path A · File-level recovery

Restores files from a Windows volume group backup of the source host onto the recovered Azure VM.

ColumnRequiredBehavior
sourceHostnameYesSource Windows host in Rubrik holding the volume group backup.
sourceFlrDriveYesSource drive letter(s). Comma separated for multiple, e.g. G,H. Trailing colons are stripped.
ClusterIn practiceMatched client side. A blank value fails the host lookup.
targetRbsWinHostNoTarget host. Defaults to tgtVMName.

./Start-FLR.ps1 -RscServiceAccountJson './rsc-service-account.json' `
  -vmCsvFile './rubrik_vm_list-2026-08-18_1317.csv' `
  -workingDir './flr_work'

# Poll status only, start nothing new
./Start-FLR.ps1 ... -CheckOnly

# Reset failed jobs to Pending and re-initiate
./Start-FLR.ps1 ... -RetryFailed

The status-check pass always runs, regardless of -CheckOnly. -CheckOnly only suppresses initiation.

What it actually does

  1. Look up the source host, matched exactly on name and cluster name. It must have at least one volume group.
  2. Get volume group snapshots over the last 90 days, grouped by day.
  3. Pick the snapshot by sorting all snapshots on the day-group end timestamp, descending, taking the first.
  4. Browse the snapshot root to validate each requested drive letter. A missing letter is a warning and that drive is dropped; all drives missing fails the job.
  5. For each valid drive, browse /<SRC>: one level deep and build one restore config per top-level entry.
  6. Look up the target host on the same cluster. Connectivity other than CONNECTED is a warning, not a failure.
  7. Fire restoreVolumeGroupSnapshotFiles with shouldIgnoreError = true.
What lands where

Every top-level item of a source drive is restored to the root of the target drive. With sourceFlrDrive = C and targetFlrDrive = D:

source C:\Data\file.txt  →  target D:\Data\file.txt

The top-level name is preserved under the target root; the source drive letter's own path component is dropped. Directory recursion is handled by the Rubrik restore engine, not enumerated by the script.

Snapshot selection caveats

Selection is by day bucket, not exact snapshot time. If several snapshots fall in the same day, the tie resolves to whatever order the API returned. isIndexed, isUnindexable and isQuarantined are queried but never used to filter, so an unindexed snapshot can be selected.

Separately, lastUpdatedTimeGt is passed StartTime in local time format here, while Start-SQLRestore.ps1 correctly uses ISO-8601 UTC. On a non-UTC host this can skew the event window.

A row missing sqlDataPath or sqlLogPath is skipped with a warning, not a hard error. Watch for that message in the output.

Dedup is first-row-wins. Unlike FLR, only the first row for a given sourceHostname|targetHost contributes settings. Keep SQL configuration on one row per server pair.

./Start-SQLRestore.ps1 -RscServiceAccountJson './rsc-service-account.json' `
  -vmCsvFile './rubrik_vm_list-2026-08-18_1317.csv' `
  -workingDir './sql_work'

./Start-SQLRestore.ps1 ... -RetryFailed

The mutation it fires

bulkExportMssqlDatabases
  finishRecovery     = true
  recoveryPoint      = { timestampMs: <now, epoch ms> }
  sourceInstanceIds  = [ SrcInstanceFid ]
  allowOverwrite     = false
  targetDataFilePath = sqlDataPath
  targetLogFilePath  = sqlLogPath
  targetInstanceId   = TgtInstanceFid
SettingConsequence
recoveryPoint = nowThere is no snapshot lookup at all. Rubrik interprets "now" as the latest recoverable point per database, log-tail inclusive. You cannot target an earlier point without editing the script.
sourceInstanceIdsThis is the instance FID, so all databases on the instance are exported. There is no per-database selection.
allowOverwrite = falseThe export fails if the databases already exist on the target instance. Drop them first on a re-attempt.
finishRecovery = trueDatabases come online rather than staying in a restoring state.

Neither path is validated for format or existence. They pass through verbatim, so a malformed path surfaces later as an RSC or SQL side failure in ErrorMessage.

sql_state.csv

Status values: Pending, Initiated, Success, Failed. There is no PartialSuccess on this path.

Status is aggregated by counting matching recovery events. Any failure count above zero sets the whole job to Failed, with ErrorMessage recording Failed: N, Success: N, Running: N — so some databases may still have restored successfully. Otherwise any running count keeps it Initiated, else Success.

Status polling is not scoped to the job

The event query filters on lastActivityType = Recovery and objectType = Mssql only, and caps at 50 events. It is not scoped to this job's instance FID. If several SQL exports run concurrently, one job's status check will count another job's events. Treat aggregate status as advisory when running more than one SQL job, and confirm in the RSC activity log.

Verify

# FLR: spot check restored content
Get-ChildItem D:\ | Select-Object -First 20

# SQL: confirm databases are online
Invoke-Sqlcmd -Query "SELECT name, state_desc, recovery_model_desc FROM sys.databases"

Prerequisites

Staging host for Phase 1

The Hyper-V role is mandatory, not just the tools

Convert-VMDK-to-VHD.ps1 calls Resize-VHD to 1 MB align the output. Those cmdlets go through the Hyper-V WMI provider, so the full role is required. Management tools alone will not work.

Install-WindowsFeature -Name Hyper-V -IncludeManagementTools -Restart

If the staging host is itself an Azure VM, you need nested virtualization: a Dv5/Dsv5 or newer SKU such as Standard_D8s_v5, on Windows Server 2022 Datacenter or newer. Alternatively deploy the "Hyper-V Server 2025" marketplace image from Cloud Infrastructure Services, which ships with the role installed.

Budget roughly 2x the total provisioned size of everything you convert in one batch. Each VM needs its VMDK download plus its fixed VHD on disk at the same time. Fixed VHD means fully allocated: a 500 GiB VMDK that is 40 GiB used still produces a 500 GiB VHD.

RSC service account

All Rubrik-facing scripts authenticate with an RSC service account JSON containing client_id, client_secret and access_token_uri.

The staging host needs direct cluster access too

Download-RubrikVMDK.ps1 opens a CDM session directly against the cluster. It derives the cluster IP from the download URL Rubrik returns, then POSTs the same credentials to https://<clusterIP>/api/v1/service_account/session. So the service account must be valid at the cluster level, and the staging host needs HTTPS reach to the cluster nodes, not just to RSC. Certificate validation is disabled for these calls.

Azure

  • Subscription, resource group, VNet and subnet already in place. The scripts create disks, NICs and VMs but do not create networking.
  • An NSG is optional. If NsgName is blank the NIC is created without one.
  • Accelerated networking is enabled on every NIC created. Confirm your VMSize supports it.
  • Contributor or equivalent on the target resource group. Login is interactive and happens once up front.

Default upload is direct-to-managed-disk. If that fails, set useStorageAccount = $true and fill in the storage account settings to upload via a page blob instead.

Constraints and gotchas

The behaviors most likely to surprise you, collected in one place.

Hard constraints

ConstraintDetail
2 TB disk limitVHD format caps at 2 TiB. Anything larger is skipped with a warning and produces no report entry. Plan an alternate path for those volumes.
Dynamic disksNot reproduced by Initialize-VMDrives.ps1. Flagged at capture, then skipped. Manual work required.
Mount point volumesVolumes mounted to a folder with no drive letter are never written to the drive info CSV. Manual work required.
Same-cluster targetsPhase 3 target hosts must be registered on the same Rubrik cluster as the source.
No per-database SQL selectionStart-SQLRestore.ps1 exports all databases on the source instance.
SQL overwrite disabledallowOverwrite = false. The export fails if databases already exist on the target.
